# Migration notes

Living log of the dependency modernization effort (backend: Strapi 4.1.3 → 5.x; frontend:
Next.js 12 → current; package manager: Yarn → pnpm). The project had not been touched in
~5 years before this started (2026-08-26).

This file records **decisions and gotchas that aren't recoverable from the code or git log**.
It does not describe the architecture — read the code for that.

## Decisions

- ~~Keep Next.js **Pages Router** (no App Router migration) — lower risk, routing is already file-based.~~ **Reversed in Stage 11**: a confirmed, unfixed Turbopack bug (Turbopack + Pages Router + custom `_document.tsx` CSS-in-JS SSR extraction) makes staying on Pages Router incompatible with using Turbopack at all. See Stage 11.
- Replace `moment` with `dayjs` everywhere — `moment` has been in maintenance-only mode since 2020, and antd 5+ expects `dayjs` anyway.
- Keep **SQLite** as the database — only swap the driver (`sqlite3` → `better-sqlite3`), no Postgres migration.
- No automated tests added as part of this effort — each stage is verified manually (boot + smoke test), then committed.
- Package manager: **pnpm**, but `backend/` and `frontend/` are **independent pnpm projects**, not a shared workspace (see Stage 4 — a shared root `pnpm-workspace.yaml` was tried first and reverted after two real cross-contamination bugs).
- Documentation: this file (`docs/MIGRATION.md`), updated as each stage completes. Records decisions/gotchas only — not architecture (read the code) and not a duplicate of the plan file used to drive the work session-to-session.

## Stage 1 — pnpm migration (no dependency version changes)

- `corepack enable pnpm`; pinned `packageManager` field in root/backend/frontend `package.json` — required, because `~/package.json` (unrelated to this repo) has `packageManager: yarn@4.9.4`, and corepack walks up parent directories looking for that field if the nearest `package.json` lacks one.
- `pnpm import` converted `yarn.lock` → a single workspace-root `pnpm-lock.yaml`.
- `sqlite3@5.0.2` would not build on Node 22 out of the box: no prebuilt binary is available any more (the old mapbox S3 host 403s) and the source build needs a `python` binary on PATH (only `python3` exists on modern macOS) — needed a temporary shim. This got fully resolved in Stage 2 by moving to `better-sqlite3`, so it's not a concern going forward.
- pnpm 11's `minimumReleaseAge`/`allowBuilds` supply-chain settings kick in on a fresh install — had to explicitly approve build scripts for legitimate native packages (`sharp`, `better-sqlite3`, `@strapi/strapi`, `@swc/core`, `esbuild`, fontawesome, core-js-pure) in `pnpm-workspace.yaml`.
- **Reversed in Stage 4**: the single shared root `pnpm-workspace.yaml` was replaced by two fully independent pnpm projects (`backend/pnpm-workspace.yaml` + `backend/pnpm-lock.yaml`, and the same for `frontend/`), no root `package.json`/`pnpm-workspace.yaml`/lockfile any more. See Stage 4 for why.

## Stage 2 — Strapi 4.1.3 → 4.26.2 (latest 4.x)

- `npx @strapi/upgrade minor` jumped straight from 4.1.3 to 4.26.2 in one step — no codemods exist for that range, so there was nothing to review beyond version bumps.
- `sqlite3` → `better-sqlite3`: **did not need to touch `config/database.js`** — Strapi ≥4.26 auto-detects which sqlite package is installed (`better-sqlite3` > `@vscode/sqlite3` > `sqlite3`) when `client: 'sqlite'` is set, so the generic client name still works.
- Strapi's own admin UI now needs `react@^18`, `react-dom@^18`, `react-router-dom@^5`, `styled-components@^5.2` as **backend** dependencies (separate from the frontend's own React/styled-components) — Strapi prompts for these interactively on first boot; added them explicitly to `backend/package.json` to avoid the interactive prompt hanging in non-interactive runs.
- Fixed two Strapi-emitted deprecation warnings (`API_TOKEN_SALT`/`TRANSFER_TOKEN_SALT` should be read via `config/admin.js`, not directly from env).

## Stage 3 — Strapi 4.26.2 → 5.52.2 (major)

- `npx @strapi/upgrade major` applied 5 of 13 available codemods (the rest were 0-affected).
- **`src/api/donation/content-types/donation/lifecycles.js`** (not identified during initial exploration — emits `newDonations` over socket.io on donation create/update/delete) got entirely commented out by the codemod, because Strapi 5 handles content-type lifecycle hooks differently once draft & publish is involved (`unpublish` firing `delete` per locale, `discardDraft` firing `create`+`delete`, etc.). Replaced with a **Document Service middleware** registered in `src/index.js`'s `register()` hook (`strapi.documents.use(...)`, filtered to `uid === 'api::donation.donation'` and the write actions `create/update/delete/publish/unpublish/discardDraft`), calling `strapi.documents(uid).findMany({ status: 'published' })` — this is the v5 equivalent of the old `publicationState: 'live'` filter. The old file was deleted (fully superseded). Verified end-to-end via the admin content-manager API + a socket.io listener.
- **`src/extensions/users-permissions/strapi-server.js`**: the upgrade codemod converted `strapi.entityService.*` calls to `strapi.documents(...)` with `documentId: "__TODO__"` placeholders. Investigating `@strapi/plugin-users-permissions@5.52.2`'s own source showed it does **not** use the Document Service for the `user` model at all — it uses `strapi.db.query()` for reads and its own service (`strapi.plugin('users-permissions').service('user')`, exposing `.fetch()`/`.edit()`/etc.) for writes, which internally resolves numeric `id` → `documentId` and hashes the password. Rewrote the override to match that pattern instead of hand-filling the `__TODO__`s. Also fixed two pre-existing (unrelated to the version bump) bugs found in the same file while at it: `strapi.query()` (removed entirely in v5, now `strapi.db.query()`) and a missing `ValidationError`/`ApplicationError` import that would have thrown `ReferenceError` on duplicate username/email or an empty password on update.
- `src/index.js`'s `bootstrap({ strapi })` and `strapi.server.httpServer` are unchanged in v5 — the socket.io setup needed no adaptation.
- **Confirmed breaking change for the frontend** (blocks Stage 9): Strapi 5.52 has no v4-compatibility flag for the REST response shape — the `{ data: { id, attributes } }` wrapper is gone unconditionally, replaced by a flat object plus `documentId`. Also confirmed directly: `PUT /api/bosses/1` (numeric id, what the current frontend sends) → `404`; `PUT /api/bosses/<documentId>` → passes routing. `lib/api/base.ts` (`flattenApiResponse`) and every `lib/api/*.ts` call site using a numeric id in the URL will need updating together with the backend cutover.
- **Unplanned finding — SQLite schema gap**: booting Strapi 5 directly against a SQLite file that originated from 4.1.3 and was never live-booted through an intermediate 4.x version can crash the built-in `core::5.0.0-discard-drafts` migration with `no such column: id` / `no such column: effect_ord` on `*_lnk` relation join tables. Cause: the join-table shape (an `id` primary key, and `<name>_ord` float ordering columns for many-to-many relations) evolved across the Strapi 4.x line after 4.1.3; a continuously-run production process picks this up transparently via ordinary schema-sync boots, but restoring an old backup and jumping straight to v5 skips that. Fix applied here: for each affected `*_lnk` table, `RENAME` → `CREATE` with an added `id INTEGER PRIMARY KEY AUTOINCREMENT` (+ `_ord` columns for the one genuine many-to-many, `collections_effects_lnk`) → `INSERT ... SELECT` the old rows across (sequential order values per group) → `DROP` the old table. Verified lossless (186/92/1/365/56/109 rows across the 6 affected tables, `PRAGMA foreign_key_check` clean). **This will very likely need to be re-applied (or pre-empted) on the production database when it's actually cut over in Stage 10** — see the checklist there.
- `engines.node` bumped to `>=20.0.0 <=22.x.x` (Strapi 5.52.2 itself supports up to Node 26; capped at 22 here because that's the LTS actually in use, not because of a v5 constraint).
- pnpm's `minimumReleaseAge` (7 days) blocked installing `@strapi/*@5.52.2` because it had just been published — added a scoped `minimumReleaseAgeExclude: ['@strapi/*']` in `pnpm-workspace.yaml` rather than disabling the policy globally.

## Stage 4 — Frontend: low-risk version bumps

- **`next build`'s typecheck had never actually been run in years** (only `next dev`, which doesn't hard-fail on type errors) — running it for the first time as a Stage 4 baseline surfaced several real, unrelated problems before any intentional version bump:
  - `@ant-design/icons` is imported directly in 12 components but was never a declared dependency (only pulled in transitively via `antd`) — worked under Yarn's flat hoisting, breaks under pnpm's strict `node_modules`. Added it as an explicit direct dependency.
  - Two earlier `pnpm clean --lockfile` runs during Stage 3 (done to fix an unrelated backend supply-chain policy issue) **re-resolved the entire workspace from scratch**, silently drifting frontend's caret-ranged deps forward from their original 2022-era pinned versions — most visibly `antd` (4.18.5 → 4.24.16) and `styled-components` (5.3.5 → 5.3.11), which broke TypeScript compilation (antd's `Button`/`Menu` JSX typing changed across those point releases). Confirmed this was pure drift, not a real regression, by building the untouched `legacy-baseline` tag with the original `yarn.lock` in a throwaway worktree — it compiled clean. Fix: pinned every frontend dependency to an **exact version** (no `^`) at whatever its currently-correct value is, so a future full-workspace re-resolution can't silently jump a not-yet-scheduled package ahead of its planned upgrade stage again.
  - `antd@4.18.5` depends on its own (newer) `moment` internally for date pickers; pnpm doesn't dedupe the way Yarn's flat hoisting did, so two separate `moment` instances existed and TypeScript treated their `Moment` types as incompatible. Fixed with a pnpm `overrides: { moment: 2.29.1 }` forcing a single instance — likely removable once Stage 5 replaces the app's own `moment` usage with `dayjs` (antd's internal copy alone won't conflict with anything at that point).
  - **The big one — shared pnpm workspace cross-contamination**: with `backend`/`frontend` in one `pnpm-workspace.yaml`, `@types/react@18` (from the Strapi 5 admin panel's `react-select`/`@emotion/react`, backend-only) and `styled-components@6.5.3` (also backend-only, via `@strapi/design-system`) were reachable inside frontend's TypeScript program and broke its typecheck, even though `pnpm why` confirmed frontend's own module resolution was untouched — this is a `next build`-specific type-inclusion effect of sharing one workspace, not a runtime bug. After patching one instance (`@types/react` override) a second, different one appeared (`styled-components@6`), which is what prompted asking the user whether to keep patching per-conflict or fix the structural cause. **Decision: split into two fully independent pnpm projects** (`backend/pnpm-workspace.yaml` + own lockfile, `frontend/pnpm-workspace.yaml` + own lockfile, no shared root) — eliminates the whole class of cross-app leakage rather than one override at a time. The `moment` override (a same-app antd conflict, unrelated to workspace sharing) still applies to `frontend/pnpm-workspace.yaml`; the `@types/react` override was dropped since backend is no longer in the same tree.
- eslint/`eslint-config-next` intentionally **not** bumped here: `eslint-config-next@12.0.8` peer-requires `eslint@^7 || ^8`, and it can't be bumped independently of Next itself (Stage 8) without breaking linting — stays pinned at the original 8.7.0/12.0.8 until then.
- TypeScript bump (4.5.5 → current) deliberately done as its own separate step after the above, not bundled together — isolates whether any new type errors come from the jump itself vs. the drift/contamination issues above. Landed on **5.9.3**, not the current latest (7.0.2):
  - `typescript@7.0.2` (the native/Go-rewrite branch) makes Next.js 12's own internal TypeScript integration code crash outright — `next/dist/lib/typescript/writeConfigurationDefaults.js` reads `ts.ScriptTarget.ESNext` from the `typescript` module in a way that no longer resolves, so this isn't a user-code type error, it's Next 12's tooling itself being incompatible with TS 7's module shape. Confirmed same crash on 6.0.3? No — 6.0.3 boots fine at the tooling level; only 7.x's rewrite breaks Next 12.
  - `typescript@6.0.3` boots but surfaces one real (if minor) type error: `import 'moment/locale/ru'` (a side-effect-only import of an untyped file) no longer resolves under 6's stricter `moduleResolution: "node"` handling. Not worth a throwaway fix since `moment` itself is being deleted in Stage 5.
  - `typescript@5.9.3` compiles and lints clean, no code changes needed. This is the Stage 4 target; the jump to 7.x is deferred to Stage 8, done together with the Next.js major upgrade (whose own codemod/tooling will be TS-7-aware) — by then `moment` will already be gone too, so the 6.x hiccup resolves itself for free.
- Also fixed along the way (real `axios@1.x` breaking change, not drift): `AxiosRequestHeaders` became a class type in axios 1.x instead of a plain object shape; `lib/api/boss.ts` and `lib/api/user.ts` built a plain headers object typed as `AxiosRequestHeaders`, which no longer type-checks. Switched both to axios's `RawAxiosRequestHeaders` type (the actual plain-object shape). Verified axios's runtime request/response/error-object behavior is unchanged for how this code uses it (no code here inspects error shapes beyond `error.response.status`/`.data`, which are unaffected).
- Landed exact Stage 4 target versions: `axios@1.19.0`, `sharp@0.35.3` (not `1.20.0`/`0.35.4` — both were published the same day and blocked by pnpm's 7-day `minimumReleaseAge`; stepped back one patch rather than adding a blanket exclude for third-party packages), `qs@6.15.3`, `ramda@0.32.0`, `classnames@2.5.1`, `styled-normalize@8.1.1`, `nookies@2.5.2` (already latest), `typescript@5.9.3`.

## Stage 5 — Frontend: `moment` → `dayjs` (partial by design)

- **Real constraint discovered, not in the original plan**: `antd@4.18.5`'s bundled `DatePicker`/`TimePicker` export types locked to `Moment` directly (`export declare type DatePickerProps = PickerProps<Moment>`, checked against the installed package's own `.d.ts`) — antd v4 does not ship a dayjs `generateConfig` out of the box, so swapping the app's own date library to dayjs would break any component that feeds its state straight into these pickers.
- 4 of the 10 files importing `moment` do exactly that: `table-row.component.tsx`, `respawn-time-column.component.tsx`, `actions-column.component.tsx`, `restart-modal.component.tsx` all thread a shared `Moment`-typed `editableTime`/`calendarDate` state directly into `DatePicker`/`TimePicker` props. Asked the user how to proceed rather than guessing: **converted the other 6 files now** (pure calculations/formatting, no antd picker coupling), **left those 4 on `moment`** until Stage 7 upgrades antd to a version with native dayjs support — at which point the remaining conversion becomes trivial instead of requiring a throwaway custom `generatePicker<Dayjs>` adapter now.
- Converted: `name-column.component.tsx`, `columns/utils.ts` (`getNewRespawnTime`), `header.component.tsx` (clock), `donations.component.tsx` + `management-block.component.tsx` (both use `.locale('ru')` — dayjs supports this the same way once `dayjs/locale/ru` is imported once), `lib/utils.ts` (`expandBoss`).
- **Real semantic difference to watch for**: moment's `.add()`/`.hours(n)` mutate the instance in place; dayjs is immutable, every call returns a new instance. `columns/utils.ts`'s `getNewRespawnTime` had a `while` loop mutating `respawnDate` via repeated `.add()` — rewritten to reassign (`respawnDate = respawnDate.add(...)`). `lib/utils.ts`'s `expandBoss` used moment's `.hours(current + interval)` setter (relying on hour-overflow to roll into the next day) — rewritten as the more direct `dayjs(boss.time).add(boss.interval, 'hour')`, same result, no reliance on setter-overflow behavior. Verified `getNewRespawnTime`'s loop logic against the original algorithm with a standalone script (10h-old timestamp + 4h interval → lands 2h before now, matching the intended "most recent past occurrence" semantics) before trusting the rewrite.
- `moment` package itself is **not yet removed** from `package.json` — still needed by the 4 deferred files (and transitively by antd's own picker internals regardless). Remove it once Stage 7 finishes the antd upgrade and the remaining 4 files are converted.

## Stage 6 — Frontend: `styled-components` 5 → 6

- Bumped `styled-components@5.3.5 → 6.5.3` and `babel-plugin-styled-components@2.0.2 → 2.3.0`. Removed `@types/styled-components` devDependency entirely — v6 ships its own types and the DefinitelyTyped package (still capped at 5.1.36) would only conflict with them.
- **Real breaking change, not just a version bump**: v6 removed its own built-in DOM-prop validation. `shouldForwardProp`'s second callback parameter used to be the library's default validator function (`(prop, defaultValidator) => !omitProps[prop] && defaultValidator(prop)`); in v6 that parameter is now `elementToBeCreated` (the styled target itself, not a function) — calling it as before fails to type-check (`Type '"symbol"' has no call signatures`) and would have failed at runtime too. Styled-components' own v6 docs now recommend transient props (`$prop`) instead of manual validation — props prefixed with `$` are automatically never forwarded to the DOM, no validator needed. Rewrote `components/scrollable/scrollable-holder.tsx`'s `ScrollableHolder` (the only place using this pattern in the app): `maxHeight`/`offset` → `$maxHeight`/`$offset`, dropped the `withConfig({ shouldForwardProp })` block and the `omitProps` map entirely. Updated the one call site (`scrollable.tsx`) to pass `$maxHeight`/`$offset`.
- Everything else needed no changes: `createGlobalStyle` (`theme/global-style.tsx`), `styled(AntButton)`/`styled(AntSelect)` extension pattern (`styled-components/button.component.tsx`, `select.component.tsx`), and the Pages-Router `ServerStyleSheet`-based SSR setup in `pages/_document.tsx` are all still valid v6 APIs unchanged from v5 for this use case.
- Verified SSR still injects styles correctly: built with `next build` + `next start` (production mode, not `next dev`) and confirmed the server-rendered `/login` HTML contains `data-styled` attributes from `ServerStyleSheet.getStyleElement()`, with no hydration-mismatch warnings.
- `next.config.js`'s top-level `styledComponents: true` option (the pre-`compiler.styledComponents` Next 12.0.x location) is currently moot either way — Next detected the custom `babel.config.json` and fell back to full Babel transform instead of SWC, so neither this option nor SWC's built-in styled-components transform is actually in effect. Not touched now — cleanup of the babel-vs-SWC setup is Stage 8/9 territory per the original plan.

## Stage 7 — Frontend: antd 4 → 5 (only — 5 → 6 deferred)

- **Real constraint discovered before touching anything**: checked npm's peer-dependency metadata for every antd 5.x and 6.x release — antd 5.x accepts `react >= 16.9.0` (fine for our still-React-17 app), but **every** antd 6.x release requires `react >= 18.0.0`. The plan's original "4 → 5 → 6" single stage is therefore impossible before Stage 8 (React 17 → 18/19) — split this stage: land on the latest antd 5.x now (`5.29.3`), defer 5 → 6 until after Stage 8. Same coupling pattern already seen with `eslint-config-next` and `typescript` in Stage 4.
- Ran the official codemod (`npx @ant-design/codemod-v5 .`, package `@ant-design/codemod-v5`, bin `antd5-codemod`) before bumping the version. It correctly did the real mechanical work — renamed `Modal`'s `visible` prop to `open` across 4 files (`restart-modal.component.tsx`, `collections-modal.component.tsx`, `header.component.tsx`, `management-block.component.tsx`) — but **mishandled one file**: in `pages/_app.tsx` it tried to comment out the now-removed `import 'antd/dist/antd.dark.css'` line but instead double-commented the comment line *above* it and left the actual CSS import untouched. Always read a codemod's diff before trusting it. Fixed by hand: replaced the CSS import with `ConfigProvider theme={{ algorithm: theme.darkAlgorithm }}` wrapping the app — v5's CSS-in-JS token system replaced the old prebuilt `antd.dark.css`/`antd.css` files entirely (they no longer exist in the package), and `theme.darkAlgorithm` is antd's own built-in equivalent of the old dark stylesheet.
- **SSR setup for the Pages Router**: antd v5's theming runs through `@ant-design/cssinjs`, which needs its own server-side extraction step alongside the existing styled-components `ServerStyleSheet`, or antd's styles simply don't render on first paint (flash-of-unstyled-content / hydration mismatch). Added `@ant-design/cssinjs`'s `StyleProvider`+`createCache` (nested inside the existing `sheet.collectStyles(...)` wrapper) and `extractStyle(cache)` (injected as a second `<style>` tag) to `pages/_document.tsx`. Added `@ant-design/cssinjs` as an **explicit direct dependency pinned to `1.23.0`** (not the standalone-latest `2.1.2`) — antd 5.29.3 depends on `^1.23.0` internally, and StyleProvider's context-based extraction mechanism only works if our own import resolves to the *exact same module instance* antd itself uses internally; a mismatched version would silently create two separate cssinjs instances and extraction would miss antd's own generated styles.
- Verified with `next build` + `next start` (production mode): the extracted `<style>` tag contains real hashed CSS-in-JS output (`data-token-hash`, `.css-<hash>` classes) with dark-theme colors (e.g. `#1668dc`), confirming `darkAlgorithm` is actually wired up and SSR extraction works — not just "no errors," but the right styles are actually present in the server-rendered HTML.
- One deprecation warning surfaced in `next dev` (not `next build`, since it's a runtime `console.warn`, not a type error): `Dropdown`'s `overlay` prop is deprecated in favor of `menu` (an `items`-array-based API). Left as-is — `overlay` still works in 5.29.3, and migrating to `menu`/`items` would mean restructuring how `header.component.tsx`, `donations.component.tsx`, and `online-list.component.tsx` render their dropdown content (they use this app's own custom `Menu`/`MenuItem`/`MenuDivider` primitives from `components/menu`, not antd's `Menu`), which is real scope beyond "make the version upgrade work." Revisit if/when antd 6 actually removes `overlay` (needs checking at that point).
- `moment` is untouched here — the antd-DatePicker-coupled files deferred from Stage 5 stay on `moment` until this stage's second half (5 → 6) actually lands post-Stage-8, since only then does antd ship dayjs support natively.

## Stage 8 — Frontend: React 17 → 19, Next.js 12 → 16, antd 5 → 6 (all deferred items landed here)

Biggest single stage of the effort. Ran `npx @next/codemod@latest upgrade latest -y`, which
correctly bumped `package.json` (Next 16.3.3, React 19.2.8, eslint 10.9.1, eslint-config-next
16.3.3) but then **crashed trying to install with plain `npm install`** instead of detecting
pnpm (`Cannot read properties of null (reading 'matches')`, an npm-internal error unrelated to
this repo) — the tool's own package-manager auto-detection failed even though `pnpm-lock.yaml`
and `packageManager: pnpm@...` were both present. Installed manually with `pnpm install` instead,
then ran the tool's *individual* codemod slugs by hand (`new-link`, `next-lint-to-eslint-cli`,
`next-image-experimental`) since the source-file transforms never ran during the failed `upgrade`
call — only the `package.json` edit had gone through.

- **Version stepping for `minimumReleaseAge`**: `next@16.3.3`, `eslint@10.9.1`, `eslint-config-next@16.3.3`, and `@types/react-dom@19.2.5` were all published within the 7-day window at install time. Stepped back to the latest release of each that cleared 7 days: `next@16.3.1`, `eslint-config-next@16.3.1`, `@types/react-dom@19.2.4` — and, separately, `eslint@9.39.5` instead of `10.x` entirely (see below, this wasn't just an age issue).
- **`new-link` codemod**: mechanical and correct — converts the old `<Link href="..."><a>text</a></Link>` pattern (required pre-Next-13) to `<Link href="...">text</Link>`, lifting any `className` on the inner `<a>` up onto `Link` itself. Touched `form-login`, `form-register`, `header.component.tsx`, `pages/404.tsx`.
- **`next-lint-to-eslint-cli` codemod**: converted `.eslintrc.json` (legacy config, deleted) to `eslint.config.mjs` (flat config) and rewrote the `lint`/`test` package.json scripts from `next lint` to `eslint .` — Next 16 removed the `next lint` subcommand entirely. The generated flat config (`defineConfig([{ extends: [...nextCoreWebVitals] }])`) worked correctly despite the tool printing a "manual migration required" warning during generation.
- **Real ecosystem-compatibility gap, not a version-pinning mistake**: `eslint@10.x` + `eslint-config-next@16.3.1`'s own declared `eslint-plugin-react: ^7.37.0` (which resolves to the actual latest, `7.37.5`) crashes outright — `eslint-plugin-react@7.37.5` calls a `context.getFilename()` method eslint 10 removed from its rule-context API (`TypeError: contextOrFilename.getFilename is not a function`). `eslint-plugin-react` had not yet shipped an ESLint-10-compatible release at the time of this upgrade. Fix: stayed on the latest `eslint@9.x` (`9.39.5`) instead — `eslint-config-next` accepts `eslint >=9.0.0` as a peer, so this is fully within its supported range, just not the newest major.
- **`next/config`'s `getConfig()` was removed** (`lib/api/base.ts` imported it to read `API_URL`/`IMAGE_URL`/`SOCKET_URL`). Next's `env` key in `next.config.js` inlines `process.env.X` into the client bundle by itself — the `getConfig().env.X` half of `process.env.X || env.X` was always redundant with the same underlying value. Simplified to plain `process.env.X` reads, `next/config` import dropped entirely.
- **`next.config.js`**: `images.domains` → `images.remotePatterns` (two entries, `http` and `https`, same hostname — `IMAGE_DOMAIN` doesn't carry a protocol and dev vs. prod differ). Top-level `styledComponents: true` (Next ≤12 location) → `compiler: { styledComponents: true }` (current location) — fixes an "Unrecognized key(s)" build warning; the babel-vs-SWC setup itself wasn't touched (still works, still prints "Using external babel configuration").
- **`next/image` legacy `layout="fill"` prop** (`header.component.tsx`, `item-image.component.tsx`) → boolean `fill` prop. The `next-image-experimental` codemod made zero changes when run against this codebase (0 of 94 files) — fixed both call sites by hand instead of chasing why the codemod didn't match.
- **The critical finding**: antd 5's `DatePicker`/`TimePicker` are typed *and behave* as **Dayjs-only** (`antd/es/date-picker/index.d.ts`: `DatePickerProps<ValueType = Dayjs | Dayjs>`) — antd 4 was Moment-only; antd dropped Moment support somewhere in the 4→5 jump. ## Stage 9 — Frontend/backend contract sync (Strapi 5's flat response + `documentId`)

- **`lib/api/base.ts`'s `flattenApiResponse` needed no code change.** It was already defensive: `flatten()` only unwraps `data.attributes` `if (data.attributes)` exists, and no-ops (returns the object as-is) otherwise. Confirmed via a real authenticated `GET /api/donations` against the live Strapi 5.52.2 backend that the actual v5 shape is now flat — `{"data":[{"id":1,...,"documentId":"..."}],"meta":{"pagination":{...}}}`, no `attributes` wrapper — and the existing code passes it through unchanged. So this file needed zero edits; only the actual `id`-in-URL call sites did (below).
- **Confirmed by direct testing against the real backend, not just reading docs**: `PUT /api/bosses/2` (numeric `id`) → `404 NotFoundError`. `PUT /api/bosses/<documentId>` → routes and updates correctly. Strapi 5's standard content-type REST routes require `documentId` (a stable string) in the URL, not the numeric `id`, which is no longer a stable identifier at all once draft&publish is involved (see next point). `users-permissions` plugin routes (`/users/:id`, `/users/me`) are **unaffected** — our overridden controller in `strapi-server.js` still takes the numeric `id` and calls `getUserService().edit(id, ...)`, which resolves numeric → documentId internally; this is the plugin's own pattern, not something this project controls.
- **Fixed**: `lib/api/boss.ts`'s `updateBossTime` now takes a `documentId: string` (renamed from `bossId: number`) and calls `PUT /bosses/${documentId}`. `BossApiResponse` gained a `documentId: string` field. Updated all 5 call sites (`table-row.component.tsx`, `actions-column.component.tsx`, `respawn-time-column.component.tsx` ×2, `restart-modal.component.tsx` ×2, `name-column.component.tsx`) to pass `boss.documentId` instead of `boss.id`.
- **Real, previously-undiscovered production data bug, found only by actually PUTing against the live backend**: `PUT /bosses/<documentId>` failed with `400 ValidationError: "world must be defined"` on the very first real test. The `boss` schema has `world: { type: "boolean", required: true, default: false }`, but **69 of 71 boss rows have `world = NULL`** in the actual SQLite data — a years-old gap between the schema's stated contract and the real data, invisible under Strapi 4 (which apparently never validated this on partial update) and only enforced starting with Strapi 5's Document Service `update`. Left as-is, this would have broken the app's core "kill boss" / edit-time feature for 69 of 71 bosses in production. **Fixed with a one-time backfill**: `UPDATE bosses SET world = 0 WHERE world IS NULL;` — safe because `null` and `false` were already behaviorally identical everywhere `boss.world` is read (falsy checks throughout the frontend), so this changes no visible behavior, only satisfies the schema's own already-stated (but previously unenforced) constraint. Checked every other `required` field across all 5 content types (`boss`, `collection`, `donation`, `effect`, `item`) for the same null-vs-required gap — `world` on `boss` was the only offender. **This must be repeated against the production database before the Strapi 5 cutover** (added to the Stage 10 checklist) — it's a one-line `UPDATE`, but it has to run once against prod's real `data.db`, same file, before the app can update any boss whose `world` is still `NULL`.
- **A second real bug, found only because updating a real record showed the numeric `id` isn't stable**: with `draftAndPublish: true` on `boss` (unchanged since Strapi 4), every `documents(uid).update()` through the standard REST PUT creates/updates a **new** row, so the boss's numeric `id` changes on every single update (observed directly: `id` went `2` → `75` → `76` across two consecutive PUTs on the same boss, while `documentId` stayed `mm1oeiufq6y8xgjbbry789af` throughout — this is the entire point of `documentId` existing). `contexts/boss-context.tsx`'s `updateBossInList` matched the boss to replace via `bossList.findIndex(({ id }) => id === boss.id)` — comparing the **new** `updatedBoss.id` (from the PUT response) against the **old** `id` values still sitting in `bossList` (from the last full fetch) — which now always fails to find a match (`index = -1`), silently no-opping the UI update (`array[-1] = boss` just adds a stray non-index property, not a real array slot) until the next 10-second poll refetch papered over it. Fixed: match by `documentId` instead (stable across updates). Also switched `boss-list-table.component.tsx`'s list `key={boss.id}` → `key={boss.documentId}`, since a churning `key` on every update was forcing React to unmount/remount each `<TableRow>` instead of reconciling in place.
- **End-to-end verification method**: booted the real Strapi 5.52.2 backend, registered a throwaway user (`stage9test`, id 138), promoted it to the `Редактор` (editor) role directly via SQL (`up_users_role_lnk`) since registration defaults to a role with no boss permissions, then issued the exact same `GET /api/bosses` and `PUT /api/bosses/<documentId>` requests the frontend now makes (same headers, same body shape) against the live backend — this is how the `world` bug and the `id`-churn bug were actually found, neither would have surfaced from `tsc`/`next build` alone. Reverted the test boss's `time`/`approximately` back to their original values, then deleted the test user and its role link (`up_users` count back to 109). Did not verify through an actual browser session (no browser automation tool available in this environment) — `tsc --noEmit` and `next build` both pass, and the API-level behavior was confirmed to exactly match what the frontend code path produces, but a manual click-through in a real browser is still worth doing before considering this stage fully closed.

## Stage 11 — App Router migration (root-causing the Stage 8 "cosmetic" cssinjs regression, in progress)

Stage 8 shipped the `@ant-design/cssinjs` `StyleProvider`/`extractStyle` wiring in `pages/_document.tsx` with `cache.cache.size === 0` at extraction time, called it a cosmetic flash-of-unstyled-content, and stopped investigating. That characterization was wrong on both counts: it wasn't cosmetic (the *entire* antd theme — dark background, every component's CSS, not just a brief flash — was missing from the raw SSR HTML, confirmed by loading pages with JavaScript disabled), and it wasn't an antd/cssinjs internals bug.

- **First real bug found and fixed along the way, unrelated to the root cause below**: `extractStyle(cache)` was called with no options, defaulting to `{ plain: false }`. In that mode `@ant-design/cssinjs` returns a string of *already-serialized* `<style ...>...</style>` tags (see `node_modules/@ant-design/cssinjs/lib/util/index.js`'s `toStyleStr`), and the code wrapped that string as the text content of *another* `<style dangerouslySetInnerHTML>` element. Since `<style>` is an HTML raw-text element, the browser feeds the literal nested-tag text straight to the CSS tokenizer instead of parsing it as HTML — invalid CSS, silently dropped. Fix: `extractStyle(cache, { plain: true })`, matching the exact pattern in `@ant-design/cssinjs`'s own README SSR example. **This fix alone did not resolve the bug** — user re-tested with JavaScript disabled and the page was still unstyled, which is what triggered the deeper investigation below.
- **Root cause, found by direct instrumentation (temporary `console.log`s patched into both the `lib/` (CJS) and `es/` (ESM) builds of `node_modules/@ant-design/cssinjs`, one file at a time, each requiring a `rm -rf .next` + dev-server restart since Turbopack doesn't watch `node_modules`)**: antd's `Space`/`Button`/`Dropdown`/etc. *do* call `useStyleRegister` during SSR (confirmed — the calls fire, with the correct `path`s). But the `cache` object they write into (verified via a direct `===` identity check logged from inside `@ant-design/cssinjs`'s own `useGlobalCache` hook) is **not** the same `cache` instance `_document.tsx` created and passed via `<StyleProvider cache={cache}>` — it's cssinjs's own disconnected module-level default/singleton cache (`defaultCache: true`), which also turned out to persist and accumulate *across separate HTTP requests* within the same dev server process (its size kept growing request-to-request instead of resetting). Every identity check that could have explained this as "two copies of the package" came back negative — same resolved file on disk (pnpm store, no duplicate `@ant-design/cssinjs` version), same `StyleContext`/`StyleProvider` object reference (checked directly, `===` true) between `_document.tsx` and a component rendered as its own descendant (`Header`). Yet a *different* descendant in the exact same render tree (`Space`, deeper than `Header`) read a different context value for the identical Context object — something only possible if Turbopack's Pages-Router SSR pipeline is running (at least) two separate render passes/module realms for the same request, one of which our custom `_document.tsx` `renderPage` override never reaches. Did not fully pin down Turbopack's internal mechanism (not this project's code to fix), but confirmed via `next dev --webpack` / `next build --webpack` that the exact same `_document.tsx` code — unchanged — works correctly under webpack: real `.ant-*` CSS rules present in the raw SSR HTML, no JS required to see a themed page.
- **Confirmed as a known, still-open upstream Next.js/Turbopack bug, not specific to this project's code or dependency choices**: [vercel/next.js#77513](https://github.com/vercel/next.js/issues/77513) (antd/cssinjs, open since March 2025, reproduced on Next 14.2 through the version in this project) and, independently, [vercel/next.js#82607](https://github.com/vercel/next.js/issues/82607) (Material UI — a completely different CSS-in-JS mechanism, same symptom). The MUI issue author's own words: *"it only seems to be an issue with BOTH turbopack and the pages router. Testing next dev without turbo seems to work, and testing with turbo but using the app router also seems to work."* Two unrelated CSS-in-JS libraries hitting the identical failure mode rules out "our antd/cssinjs setup is wrong" — this is a Turbopack + Pages Router + custom `_document.tsx` combination bug, full stop.
- **Interim fix, already shipped**: `package.json`'s `dev`/`build` scripts now run `next dev --webpack` / `next build --webpack` (Next.js's own supported bundler-opt-out flag). Verified both in dev and via a real `next build && next start` that real antd CSS ships in the SSR HTML. This is *not* the final state — it forgoes Turbopack's speed for as long as the project stays on Pages Router.
- **Decision**: migrate to the App Router (reversing the Stage 0 decision recorded above), specifically because App Router + Turbopack is confirmed unaffected by this bug — going back to Turbopack is the actual goal, `--webpack` is a stopgap. Migration is incremental (`pages/` and `app/` coexist for routes not yet migrated), route by route, with `--webpack` staying in `package.json` until every route and `pages/_app.tsx`/`_document.tsx` are gone. ### Phase 1 — App Router foundation (layout, registries, auth, proxy)

Landed: `app/layout.tsx` (root layout replacing `pages/_app.tsx`+`pages/_document.tsx` for everything mounted under `app/`), `app/styled-components-registry.tsx` (the official Next.js styled-components App Router pattern — `ServerStyleSheet` + `useServerInsertedHTML`), `@ant-design/nextjs-registry`'s `AntdRegistry` for antd/cssinjs SSR extraction (a proper, App-Router-native mechanism — `useServerInsertedHTML`-based, architecturally nothing like the broken `_document.tsx` `renderPage` override), `lib/get-current-user.ts` (server-only `cookies()` + `/users/me` fetch, replacing the relevant half of `_app.tsx`'s `getInitialProps`), `frontend/proxy.ts` (the auth-redirect gate — **not** `middleware.ts`: Next.js 16 deprecated and renamed the `middleware` file convention to `proxy` mid-cycle, exporting a `proxy` function instead of `middleware`; same functionality, different file/export name, caught by reading `node_modules/next/dist/docs` per this repo's own `AGENTS.md` rule instead of writing the old convention from memory).

- **A second, unrelated-to-Turbopack theming bug found and fixed during this phase**: after wiring everything up, antd components rendered with **light-theme colors despite `ConfigProvider theme={{ algorithm: theme.darkAlgorithm }}`** — confirmed via a temporary token probe (`theme.useToken()` rendered to the page) that `colorBgContainer` was `#ffffff` (light) instead of the expected dark value, identically with JavaScript disabled (so it's an SSR-time bug, not a hydration mismatch). Root cause, found by logging `Object.keys(theme)` where `theme` was imported (`import { theme } from 'antd'`) directly at the top of `app/layout.tsx`: **`theme` came back as `{}`, an empty object** — `theme.darkAlgorithm` was `undefined`, so `ConfigProvider` silently fell back to its default (light) algorithm. The same import line worked fine in the old `pages/_app.tsx`. Root cause: `app/layout.tsx` is a Server Component, and antd's `theme` barrel module transitively pulls in code marked `"use client"`; the RSC bundler can generate a proper client reference for actual React components re-exported from a client-tainted module, but `darkAlgorithm` is a plain function/data value sitting in that same module, not a component — importing it directly into a Server Component file appears to silently produce a stripped/empty stand-in rather than an error. **Fix**: never import antd's `theme` (or anything else non-component from a client-tainted antd submodule) directly into a Server Component. Moved the `ConfigProvider`+`theme` usage into its own tiny Client Component (`app/antd-theme-provider.tsx`, `'use client'`), composed into `layout.tsx` the same way `Header`/`AuthContextProvider` already are. This is a **general rule for the rest of this migration**, not just this one call site: any non-component export from a package that has 'use client' anywhere in its module graph must be imported from a Client Component, never straight into a Server Component file, even if nothing in the Server Component actually renders it as JSX.
- Verified via a temporary `app/dev-check/page.tsx` (deleted once verification passed): dark theme, styled `Button`/`Select` (custom `styled(AntdComponent)` wrappers from `styled-components/`), and the shared `Header` all render correctly, identically with JavaScript disabled — confirmed on the real dev server (still running under `--webpack`, per the phase's own stated constraint that the bundler is process-wide, not per-router).

### Phase 2 — Simple and redirect-only routes

Landed: `app/not-found.tsx` (← `pages/404.tsx`), `app/profile/page.tsx` and `app/users/[userId]/page.tsx` (← the two redirect-only `pages/**/index.tsx` files, now using `redirect()` from `next/navigation`; note `params` is a `Promise` in this Next version and must be `await`ed, per `node_modules/next/dist/docs`), `app/login/page.tsx` and `app/register/page.tsx` (← `pages/login.tsx`/`pages/register.tsx`, both now `'use client'` since they read `useAuthContext().loggedIn`). `pages/api/hello.ts` (unused `create-next-app` scaffold, confirmed via grep that nothing referenced it) deleted outright.

- **Build-breaking correction to the Phase 1 "coexistence" assumption**: as soon as an `app/` file existed at the same route as a `pages/` file, `next dev` refused to build at all: *"Conflicting app and page files were found... pages/login.tsx - app/login/page.tsx"* (×4, for all the routes landed this phase). Fixed by deleting the four old `pages/` files immediately — see the correction added to the Stage 11 intro above. This changes the practical execution order for every remaining phase: create the `app/` replacement **and** delete the `pages/` original in the same step, then verify — there is no window where both can be tested side by side.
- **`components/form-login/index.ts` and `components/form-register/index.ts` used `next/dynamic(() => import(...), { ssr: false })`** to lazy-load the form component. This pattern is rejected by the App Router build (`ssr: false` is not allowed for `next/dynamic` inside a Server Component) and was unnecessary anyway — neither form component touches any browser-only API, the `ssr: false` was pure legacy caution. Both forms now `'use client'` themselves and the barrel files are plain re-exports (`export { default as FormLogin } from './form-login.component'`); `useRouter` in both moved from `next/router` to `next/navigation`.
- **`proxy.ts`'s route matcher was too narrow and broke a working feature**: `/owl.png` (a `next/image` local image on the new 404 page) failed with a 400 `"The requested resource isn't a valid image."` — traced to `sharp` receiving non-image bytes. Root cause: Next's image optimizer, for a *local* (`public/`) image, makes an **internal mocked HTTP request back into the app** for the raw file bytes — that internal request's path is the bare `/owl.png`, not anything under `/_next/image/...`. The matcher's negative-lookahead only excluded `api`, `_next/static`, `_next/image`, and three named files (`favicon.ico`, `sitemap.xml`, `robots.txt`) — copied directly from Next's own doc example, which is explicitly a minimal illustration, not a complete real-world exclusion list. `/owl.png` matched none of those exclusions, so the auth-redirect logic ran against Next's own internal image-fetch request and returned an HTML redirect instead of image bytes. Fixed by excluding any path ending in a common static-asset extension (`ico|png|jpg|jpeg|gif|webp|svg|css|js|woff|woff2|ttf|xml|txt|json`) rather than naming individual files. **Anything using `next/image` against a `public/`-hosted file needs this covered by the proxy's exclusion list** — worth rechecking if new static asset types get added later.
- **A real, pre-existing CSS specificity fragility, exposed (not introduced) by this phase's changes**: after the two fixes above, `/` (still `pages/index.tsx`, untouched this phase) rendered its boss list table with the "reduce/increase time" and "mark not respawned" icon-buttons **permanently visible, stacked vertically instead of absolutely positioned and hover-only**. Root cause, found via direct browser DevTools inspection (not guessing) walking `.reduceButton`'s compiled CSS-module rule (confirmed present via `[...document.querySelectorAll('style')].some(s => s.textContent.includes('reduceButton'))`) down to the Styles panel: `boss-list-table.module.css`'s `.reduceButton { display: none; position: absolute; ... }` was present and correctly matched but shown **struck through**, overridden by antd's own `:where(.css-dev-only-do-not-override-xxxxxx).ant-btn { display: inline-flex; position: relative; ... }`. antd deliberately wraps its own hash class in `:where()` to *reduce its effective specificity to zero*, specifically so same-specificity user CSS can override it — but that trick only works if antd's base style tag is inserted into `<head>` **before** the user's CSS-module style tag; here the order had flipped (both are runtime-inserted — antd via its cssinjs `useInsertionEffect` "prepend queue", CSS Modules via webpack's dev-mode style-loader — and which one's JS runs first is a module-evaluation-order question, not something explicitly controlled). Did not chase exactly which of this migration's changes (new `@ant-design/nextjs-registry` dependency, new `'use client'` directives on files also imported by the still-untouched `pages/_app.tsx`) tipped that ordering, because **this exact codebase already has an established, working fix for this exact problem**: `boss-list-table.module.css`'s own `.nameColumn.nameColumn` / `.respawnColumn.respawnColumn` rules (pre-existing, untouched by this migration) double the class in the selector specifically to raise specificity above antd's `:where()`-neutralized base class, making the override win **regardless of `<style>` tag insertion order**. Applied the same doubling to the two classes that weren't already using it and were now losing the race: `.reduceButton.reduceButton`, `.increaseButton.increaseButton`, `.remainingButton.remainingButton` (boss-list-table.module.css), and `.outDateIcon.outDateIcon` (same file, the "?" mark-not-respawned button in the Name column, which had the identical symptom). Grepped every other `.module.css` in the project for the same shape (a class doing `position: absolute`/`display: none` applied to an antd `Button`/component, not doubled) — no other instances found, but this is worth re-checking per-page as the remaining phases land, since the underlying insertion-order race is not actually fixed, only worked around at every currently-known call site.

### Phase 3 — List/fetch routes (`/`, `/users`)

Landed: `app/page.tsx` (← `pages/index.tsx`, boss list) and `app/users/page.tsx` (← `pages/users/index.tsx`), both thin async Server Components that read the `jwt` cookie via `(await cookies()).get('jwt')?.value` and fetch (`getBossList`, or `Promise.all([getUsers, getRoles])`) — the existing `lib/api/*` functions needed no changes, confirmed in Phase 1's inventory to be plain `axios` with no Pages-Router assumptions. - **`components/user-list-table/user-list-table.component.tsx`'s `next/router` usage had to move up from Phase 4 into this phase**, not deferred as originally planned: `next/router`'s `useRouter()` throws outright when rendered outside the Pages Router's own context provider, which doesn't exist under `app/`. Anything using `next/router` that ends up mounted under `app/` — even transitively, even if the migration plan filed it under a later phase — breaks immediately, not gracefully. **Rule for the rest of this migration**: `next/router` usages can only stay unmigrated in components that are *exclusively* reachable from still-unmigrated `pages/` routes; the instant a component becomes reachable from any `app/` route (directly or through a shared child), its `next/router` calls must move to `next/navigation` in the same step, regardless of which phase the plan originally assigned it to.
- Also marked `contexts/boss-context.tsx` and `components/boss-list-table/boss-list-table.component.tsx` `'use client'` (both call hooks directly) — no surprises, matches the pattern established in Phase 1.
- Minor drive-by fix while rewriting the users-list sort: the original `pages/users/index.tsx` did `users.sort(...)` directly on the prop array (in-place mutation of a value that, in the old Pages Router world, was a fresh `getServerSideProps`-returned array every render so the mutation was harmless — but it's still the same category of "mutate what you were handed" smell flagged for `boss-context.tsx` in Stage 8). Changed to `[...users].sort(...)` in the new `UsersContent` component while it was already being rewritten.

### Phase 4 — Dynamic Tabs routes (`/profile/[type]`, `/users/[userId]/[type]`)

Landed: `app/profile/[type]/page.tsx` and `app/users/[userId]/[type]/page.tsx`, both async Server Components that validate the `type` param (`'management' | 'collections'`, else `notFound()` from `next/navigation`) and fetch roles (and, for the second route, the target user) before handing off to new Client Components (`components/profile-content/`, `components/user-profile-content/`) for the `useAuthContext()` gate + antd `Tabs`. `Tabs`' `onChange` handler got simpler, not just ported: the old code built the next URL by string-replacing the literal `[type]`/`[userId]` bracket tokens out of `router.pathname` (a Pages-Router-only API); the App Router version just does `` router.push(`/profile/${key}`) `` / `` router.push(`/users/${user.id}/${key}`) `` directly — no pathname template to reverse-engineer. `components/management-block` and the two new Tab-content wrappers moved to `next/navigation`.

Landed: deleted `pages/_app.tsx`, `pages/_document.tsx` (and the now-empty `pages/` directory itself), and `lib/server-redirect.ts` (its only caller was `_app.tsx`; it also imported the `next/router` singleton `Router` object, the last remaining `next/router` reference in the codebase). `package.json`: `dev`/`build` scripts dropped `--webpack` (Turbopack is Next 16's default, no flag needed), and the now-fully-dead `babel-plugin-styled-components` devDependency was removed (its config file, `babel.config.json`, was already deleted earlier in this same Stage 11 investigation, before the Turbopack root cause was found — `compiler.styledComponents: true` in `next.config.js` has been the live SWC-based mechanism since then, so the package itself was just leftover weight).

- **Verified the actual bug this whole migration exists to fix is gone, under the real conditions that matter**: `rm -rf .next && pnpm build` (clean Turbopack production build, no errors) → `pnpm start` → `curl`'d `/` unauthenticated (307 to `/login`, proxy still gating correctly) and `/login` directly — real `.ant-btn*` CSS rules present in the raw SSR HTML (not just class names with no matching rules, which was the original symptom). This is the same verification method used to originally characterize the bug in Stage 11's opening section, now confirmed clean on Turbopack + App Router + a real production build, not just `next dev`.
- Remaining manual verification (browser, both dev and prod, JS-enabled and JS-disabled): full click-through of every route, login/register/logout, role-gated UI, the two Tab pages, image loading, WebSocket online-list — see the migration plan's own verification checklist.
- **A real, previously-silent hydration-mismatch bug surfaced during this manual pass, on `/users`**: React's dev-mode hydration warning fired for `<Input>`'s `id` attribute (server: `input-6996`, client: `input-2220`, different every load). Root cause: `lib/generate-id.ts`'s `generateId()` used `Math.random()` to build the id/label pairing, called from `components/input/input.component.tsx` via `useState(() => generateId())` — this always produces a different value on the server render vs. the client's hydration render, textbook non-deterministic-SSR-input, one of the specific cases React's own hydration-mismatch message calls out by name. This almost certainly wasn't introduced by the migration — `Math.random()` in `useState`'s lazy initializer behaves identically under Pages Router SSR — but the App Router's dev overlay appears to surface hydration mismatches more prominently than the old Pages Router setup did, which is plausibly why it went unnoticed until now rather than being new. Fixed with React's actual purpose-built tool for this: `useId()`, which is guaranteed identical between server and client render. `lib/generate-id.ts` had no other callers and was deleted.

## Stage 12 — Real fixes for the 10 `eslint-plugin-react-hooks@7` findings Stage 8 deferred

Requested directly: fix all 10 with real best-practice solutions, not `eslint-disable`. None of the 10 were caused by, or touched during, the App Router migration (Stage 11) — confirmed via `pnpm lint` before starting that the count and file list exactly matched Stage 8's original catalogue, plus the one already fixed in Stage 11 (`auth-context.tsx`'s `loggedIn`). The React Compiler *build transform* is still not enabled in this project (checked again: no `experimental.reactCompiler`, no `babel-plugin-react-compiler`) — only the lint-time static analysis runs — so none of this was a runtime bug; the value was in the fixes themselves being genuine improvements, not in unblocking anything.

- **`actions-column.component.tsx`'s `useState(false)` + `useEffect(() => setMounted(true), [])` mount-flag** (`react-hooks/set-state-in-effect`) — almost certainly there to dodge a `dayjs(boss.time).format('HH:mm')` hydration mismatch from server (Node.js) vs. browser running in different local timezones. Replaced with React's own documented primitive for exactly this "render differently after hydration" case: a tiny new `lib/hooks/use-is-client.ts` built on `useSyncExternalStore` (subscribe is a no-op, `getSnapshot` returns `true`, `getServerSnapshot` returns `false`) — identical rendered behavior, zero `setState` calls, so the rule doesn't fire on it at all. Single call site in the codebase for this pattern (checked via grep before writing the fix).
- **`scrollable.tsx`'s `handlerMouseUp` self-reference** (`react-hooks/immutability`, a genuine TDZ-shaped smell: the callback removed its own `mouseup` listener from inside its own body) — realized the `mouseup` listener only ever needs to fire once per drag cycle anyway, so switched the `addEventListener('mouseup', ...)` call site to the native `{ once: true }` option, which makes the browser remove that listener automatically. `handlerMouseUp`'s body now only removes `mousemove` (the listener that *does* need repeated firing), no self-reference left, and the pointless `dragging` ref was dropped from its dependency array in the same pass.
- **`scrollable.tsx`'s `useLayoutEffect` reading `scrollHostRef.current?.clientHeight`/`scrollHeight` in its dependency array** (`react-hooks/refs`, reported as 5 separate spans for the same root cause) — this was flagged correctly on more than a style level: dependency arrays are evaluated during render, and **ref mutations are never tracked by React as a reactive dependency at all**, so this array entry never actually did anything — the effect only ever re-ran because `thumbHeight`/`maxHeight` (real dependencies, also in the array) changed to trigger it. Stage 8 had already identified the correct fix as a `ResizeObserver` and explicitly deferred it as out of scope; implemented it now: extracted a ref-free `recalculateThumbHeight` callback that reads the ref only *inside* its own body (fine — that's an event-handler/effect context, not render) and uses a functional `setThumbHeight` update (so it no longer needs `thumbHeight` as a dependency either); a `useLayoutEffect` drives it on real prop/content changes (`maxHeight`, `children`); a second, new `useEffect` mounts a `ResizeObserver` on the actual host element and calls the same callback on genuine box-resize events (window resize, layout shifts) that no prop or state change would ever surface. No `ref.current` appears in any dependency array anymore.
- **`collection-context.context.tsx`'s three `useCallback`s calling `setActiveIds`/`setUsetCollections` without listing them as dependencies** (`react-hooks/preserve-manual-memoization`) — these are `useState` setters, guaranteed referentially stable by React, so the classic `exhaustive-deps` rule always allowed omitting them; the newer Compiler-aware inference doesn't special-case setters the same way and flags the textual mismatch between what the closure references and what the array declares. Added them explicitly to all three arrays (`handleActiveReset`, `handleItemClick`, `handleToggleClick`) — zero behavior change (stable references never cause the memoized callback identity to change), just makes the dependency arrays honestly describe what the closures touch.
- **Verification**: `pnpm lint` went from 10 errors to 0. `npx tsc --noEmit` stayed clean throughout. `rm -rf .next && pnpm build` (Turbopack production build) still compiles cleanly with the same route list as Stage 11's Phase 5 build. Manual browser re-check still pending for the actual interaction surfaces touched (drag-scrolling the donations/online-list dropdowns in the header — the only two consumers of `Scrollable`, confirmed via grep — and a boss row's action buttons appearing without a hydration warning).
