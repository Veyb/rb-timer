## Context

See proposal.md - Why/What Changes for motivation and scope. Concrete facts gathered from the current tree that shape this design:

- `apps/backend` has zero `devDependencies` and no `tsconfig.json`; all 5 content-types (`boss`, `collection`, `donation`, `effect`, `item`) are one-line `createCoreController`/`createCoreService`/`createCoreRouter` factory calls (15 files total). Real logic lives only in `src/index.js` (socket.io register/bootstrap) and `src/extensions/users-permissions/strapi-server.js` (custom `/users/me` endpoints).
- `apps/backend/types/generated/{contentTypes,components}.d.ts` already exist today, generated by Strapi 5 even for a JS project. They import `Schema, Struct` from `@strapi/strapi` and are what the typed `createCoreController<'api::boss.boss'>` generics consume once the project is TS.
- Strapi 5's own `@strapi/typescript-utils` ships two tsconfig presets (read directly from `node_modules/.pnpm/@strapi+typescript-utils@5.52.2/.../tsconfigs/`):
  - `server.json`: `module: CommonJS`, `moduleResolution: Node`, `target: ES2019`, `strict: false`, `skipLibCheck: true`, `forceConsistentCasingInFileNames: true`, `incremental: true`, `esModuleInterop: true`, `resolveJsonModule: true`, `noEmitOnError: true`, `noImplicitThis: true`.
  - `admin.json`: `module: ESNext`, `moduleResolution: Bundler`, `target: ESNext`, `strict: true`, `jsx: react-jsx` - for the admin-panel webpack/vite bundle, not app code.
- `@strapi/typescript-utils@5.52.2` is present in `pnpm-lock.yaml` only as a transitive dependency of `@strapi/strapi`; pnpm's strict per-package `node_modules` does **not** expose it at `apps/backend/node_modules/@strapi/typescript-utils` (verified: only `plugin-users-permissions` and `strapi` are hoisted there). A `tsconfig.json` `extends` pointing at it would fail to resolve unless it's added as an explicit `devDependency`.
- `@strapi/typescript-utils@5.52.2` itself depends on `typescript@5.9.3` and uses that bundled compiler internally for `strapi build`/`strapi develop`'s own TS-compile step - **not** whatever `typescript` version `apps/backend` declares as its own devDependency. Confirmed directly: `strapi build` fails when the project's own tsconfig carries an option only valid for a newer TS (see Decisions).
- `apps/frontend/tsconfig.json` today inlines: `target: ES2017`, `lib: [ES2022, DOM, DOM.Iterable]`, `module: preserve`, `moduleResolution: bundler`, `strict: true`, `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noFallthroughCasesInSwitch`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `allowUnusedLabels: false`, `allowUnreachableCode: false`, `verbatimModuleSyntax: true`, plus the Next `plugins: [{name: "next"}]` and its typed-routes `include` list. These were deliberately chosen in the archived `modernize-frontend-tsconfig` change and must not regress.
- `pnpm-workspace.yaml`'s `packages:` list is literal paths (`apps/frontend`, `apps/backend`), not a glob - the project's established convention, not something this change should silently switch to globbing.
- User decisions locked in during exploration: convert all of `apps/backend/src` and `config` in one pass (not incrementally); backend tsconfig stays `strict: false` matching Strapi's own preset; shared package is named `packages/typescript-config`; this is its own standalone OpenSpec change (not folded into the tracked dependency-upgrade effort).

## Goals / Non-Goals

**Goals:**
- Backend builds and runs identically to today (`strapi develop`/`strapi build`), now via TypeScript, with no behavior change to the socket.io bootstrap, the `users-permissions` extension, or any content-type.
- A real, reusable `packages/typescript-config` package that both apps extend - not two configs that merely look similar.
- Backend's TypeScript posture matches Strapi's own upstream server preset (`strict: false`) rather than importing frontend's strictness wholesale, since Koa's `ctx` typings and the plugin extension pattern (`plugin.controllers.user.me = ...`, `strapi.io = io`) are not strict-clean.

**Non-Goals:**
- No change to `apps/backend`'s ESLint setup (`.eslintrc`/`.eslintignore` stay as-is, even though Strapi's own guide suggests deleting them) - linting/formatting unification is explicitly a separate, later, root biome+lefthook effort per existing project memory.
- No Strapi version bump, no content-type schema changes, no new API behavior.
- No production deploy impact - this is local/dev tooling only; the existing dependency-upgrade plan's Stage 10 (prod cutover) is unaffected and unblocked separately.
- `src/admin/tsconfig.json` does not route through the new shared package (see Decisions) - it's Strapi's own generated admin-panel shell, not app code this repo owns the shape of.

## Decisions

**`packages/typescript-config` holds only genuinely runtime-independent options in `base.json`.** Rather than putting `strict: true` in `base.json` and overriding it back to `false` in `strapi-server.json`, `base.json` only carries options with no dependency on module system or strictness posture: `skipLibCheck`, `esModuleInterop`, `resolveJsonModule`, `forceConsistentCasingInFileNames`, `incremental`, `noFallthroughCasesInSwitch`, `allowUnusedLabels: false`, `allowUnreachableCode: false`. The full "strict family" (`strict`, `noUnusedLocals`, `noUnusedParameters`, `noImplicitReturns`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `verbatimModuleSyntax`) and all module/target/resolution settings live entirely in `nextjs.json` and `strapi-server.json` respectively, declared explicitly rather than inherited-then-unset.
- *Alternative considered*: put everything frontend has today into `base.json` and have `strapi-server.json` override the strict-family flags back off. Rejected - an `extends` chain that declares something in the parent only to immediately cancel it in every non-frontend child is a sign the option was never actually shared; it also silently re-includes those flags for any *third* future preset that forgets to override them.

**`strapi-server.json` extends `@strapi/typescript-utils/tsconfigs/server` directly, not through our own `base.json`.** Strapi's own preset already encodes the constraints that matter for the server (CommonJS, ES2019, `noEmitOnError`, `noImplicitThis`); layering our `base.json` on top only adds the small shared list above. `apps/backend/tsconfig.json` becomes: extends `@rb-timer/typescript-config/strapi-server.json`, with the project-specific `outDir: dist`, `rootDir: .`, `include`/`exclude` (per Strapi's guide) added locally.
- *Alternative considered*: have `strapi-server.json` re-derive Strapi's settings by hand instead of extending Strapi's own preset. Rejected - duplicating Strapi's preset means it silently drifts whenever Strapi changes its own recommended server config on a future upgrade.

**`src/admin/tsconfig.json` extends `@strapi/typescript-utils/tsconfigs/admin` directly**, per Strapi's documented guide, untouched by this repo's shared package. It compiles the admin-panel webpack/vite bundle, not application code, and isn't a surface this repo has an opinion about.

**`typescript` is unified to a single version, `5.9.3`, across the whole monorepo, via a pnpm workspace catalog - not split per app.** This directly supersedes two earlier decisions in this same file: the original "pin to frontend's `6.0.3`" and the later "each app pins whatever its own build pipeline actually uses." Both were reasonable given what was known at the time, but a follow-up question ("can frontend go down to `5.9.3` instead of forcing backend up to `6.0.3`?") wasn't checked before landing on the split. It was checked directly afterward: nothing in frontend's toolchain requires `6.0.3` specifically - `eslint-config-next`'s own peer range is `"typescript": ">=3.3.1"` (no `6.0` floor), and the archived `modernize-frontend-tsconfig` change that originally bumped frontend from `5.9.3` to `6.0.3` says outright that "`6.0.3` is the same compiler engine as `5.9.3` ... a low-risk version bump with no behavioral surprises" - i.e. the bump was "why not go one step further" modernization, not a requirement. Backend, on the other hand, genuinely cannot reach `6.0.3`: confirmed by reading `@strapi/typescript-utils`'s compiled source directly (`dist/compilers/basic.js`: `var ts = require('typescript')`) that it always resolves and runs its own bundled `5.9.3` regardless of what `apps/backend` declares, and `strapi-server.json`'s inherited `moduleResolution: "Node"` cannot satisfy both 5.9.3's and 6.0.3's differing rules at once (tested directly - see the superseded reasoning below). Since only one direction is actually free of constraints, unifying downward to `5.9.3` was the available path to a single version everywhere, and was verified to regress nothing (`tsc --noEmit` clean on both apps under `5.9.3`, both `next build` and `strapi build` clean, all from a from-scratch `pnpm install`).
- *Superseded reasoning, kept for context*: pinning backend to `6.0.3` while Strapi's real build engine stays on `5.9.3` was never achievable without one of the two paths breaking - `strapi build` failed outright with `TS5103: Invalid value for '--ignoreDeprecations'` when the shared tsconfig carried `ignoreDeprecations: "6.0"` (needed to silence `6.0.3`'s hard error on the deprecated `moduleResolution: "Node"`, but rejected as an invalid value by the bundled `5.9.3`); no single value satisfies both compilers (tested: `"5.0"` is accepted by `5.9.3` but doesn't silence `6.0.3`'s error). Switching `moduleResolution` to a non-deprecated equivalent (`nodenext`) was also considered and rejected - it requires `module: "NodeNext"` too (verified directly), a materially larger deviation from Strapi's own CommonJS server preset than a version choice.

**`packages/typescript-config`, `apps/backend`, and `apps/frontend` reference `typescript` and `@types/node` via `pnpm-workspace.yaml`'s default `catalog:` (`"typescript": "catalog:"`, `"@types/node": "catalog:"`), instead of repeating literal version strings in three `package.json` files.** `@strapi/typescript-utils` (pinned to the same version as `@strapi/strapi`, `5.52.2`) is also catalogued, since `apps/backend` and `packages/typescript-config` both need it at the identical version. Runtime dependencies that are *intentionally* different per app (`react`: `19.2.8` in frontend vs `^18.0.0` in backend; `styled-components`: `6.5.3` vs `^6.0.0`) are deliberately **not** catalogued - forcing those into lockstep would be a real, unrelated dependency-bump decision (with actual bundling/runtime risk, per the Stage-4 leak class documented in `openspec/changes/archive/2026-09-05-adopt-pnpm-monorepo/design.md`), not a tooling-config change like this one.
- *Alternative considered*: catalog every shared-name dependency indiscriminately. Rejected - a catalog entry is a policy statement ("these must always match"), and `react`/`styled-components` differing per app is deliberate, not drift to be fixed.

**Backend conversion happens as a single pass across all of `src/` and `config/`, not file-by-file with `allowJs: true` bridging.** Given 15 of ~20 files are one-line factory boilerplate and only 2 files carry real logic, incremental bridging adds process overhead (tracking partial state) without reducing real risk. `allowJs` is still set to `true` in the root tsconfig per Strapi's guide as a safety net, not as the migration strategy itself.

**`pnpm-workspace.yaml` gets one new literal line, `packages/typescript-config`,** consistent with the existing literal (non-glob) style for `apps/frontend`/`apps/backend`. Future shared packages (e.g. the planned `packages/biome-config`) each add their own line the same way; switching the whole file to a `packages/*` glob is a separate, out-of-scope decision about workspace conventions, not something to fold into this change.

**`strapi-server.ts`'s `lodash` dependency is removed entirely (not swapped for `ramda`, frontend's utility library).** Diffed the file against Strapi's own `@strapi/plugin-users-permissions/dist/server/controllers/user.js` and found it's a near-verbatim copy (a documented Strapi pattern: copy the built-in controller, then modify) - `lodash` was never a deliberate choice for this project, it just came along from copying Strapi's own source, which itself depends on `lodash` internally. The only usage anywhere in the file is `_.has(object, key)`, six times, always on a plain object's own top-level string key - `Object.prototype.hasOwnProperty.call(object, key)` is the exact native equivalent, requires no `lib` bump (unlike `Object.hasOwn`, ES2022), and needs no dependency at all.
- *Alternative considered*: swap to `ramda` (`R.has(key, obj)`) for cross-monorepo utility-library consistency with frontend. Rejected - it would still add a new dependency to `apps/backend` (ramda has never been a backend dependency), and its argument order is reversed from lodash's (`R.has(key, obj)` vs `_.has(obj, key)`), a subtle transcription risk for no real gain over the native one-liner. `lodash` itself isn't a real weight concern here either way - it's backend Node code (no browser bundle to inflate) and was already loaded into the process transitively via `@strapi/strapi`/`@strapi/utils` regardless of whether this file declared it directly.

## Risks / Trade-offs

- **[Risk]** `@strapi/typescript-utils` version pinned separately from `@strapi/strapi` can drift on a future upgrade, silently reintroducing a preset mismatch. → **Mitigation**: note the pairing in `apps/backend/package.json` comments are not possible in JSON, so document it in tasks.md's verification step and re-check on the next Strapi bump.
- **[Risk]** `strict: false` on the backend means type errors that strict mode would catch (e.g. in the socket.io bootstrap or the users-permissions extension) go unflagged. → **Mitigation**: accepted trade-off, matches Strapi's own upstream recommendation; can be revisited per-file later if desired without touching the shared preset (a file can locally opt into stricter checks via inline TS comments if ever needed).
- **[Risk]** The SQLite `database.ts` path fix (extra `'..'` once compiled into `dist/config/`) is exactly the kind of silent path bug that already bit this project once during the Strapi 5 `_lnk` migration (see project memory). → **Mitigation**: fix is called out explicitly in tasks.md; verify by booting `strapi develop` from the compiled output and confirming it opens the existing `.tmp/data.db` at the repo root, not a new empty one under `dist/`.
- **[Risk]** Converting all ~20 files in one pass makes for one large diff/review instead of several small ones. → **Mitigation**: accepted trade-off per explicit user choice, justified by the small, low-complexity surface area (confirmed file-by-file during exploration).
- **[Risk]** Existing `types/generated/*.d.ts` were generated for a JS project; need to confirm they still resolve correctly (import path, `Struct`/`Schema` types) once the project itself is TS and factories become generic (`createCoreController<'api::boss.boss'>(...)`). → **Mitigation**: regenerate via `strapi ts:generate-types` as part of the conversion and diff against the existing files rather than assuming they're already correct.

## Migration Plan

1. Create `packages/typescript-config` (`package.json` with `name: "@rb-timer/typescript-config"`, `private: true`; `base.json`, `nextjs.json`, `strapi-server.json`).
2. Add `packages/typescript-config` to `pnpm-workspace.yaml`; add it as a `workspace:*` devDependency to both `apps/frontend/package.json` and `apps/backend/package.json`; `pnpm install`.
3. Rewrite `apps/frontend/tsconfig.json` to `extends: "@rb-timer/typescript-config/nextjs.json"` plus its Next-specific `include`/`exclude`/`plugins`. Verify `pnpm --filter frontend build` stays clean (same baseline as today).
4. Add `@strapi/typescript-utils` (pinned `5.52.2`), `typescript` (`5.9.3` - matching what `@strapi/typescript-utils` itself bundles for the real build, not frontend's `6.0.3`; see Decisions), `@types/node` (matching engines range) as `devDependencies` in `apps/backend/package.json`.
5. Add `apps/backend/tsconfig.json` (extends `@rb-timer/typescript-config/strapi-server.json`, sets `outDir: dist`, `rootDir: .`, `allowJs: true`, Strapi's recommended `include`/`exclude`) and `apps/backend/src/admin/tsconfig.json` (extends `@strapi/typescript-utils/tsconfigs/admin` directly).
6. Convert all `apps/backend/src/**/*.js` and `apps/backend/config/*.js` to `.ts` in one pass, including the `database.ts` path fix. Use the typed `createCoreController<'api::boss.boss'>('api::boss.boss')` form (etc.) for the 5 content-types' controllers/services/routes.
7. Run `strapi ts:generate-types`; diff the regenerated `types/generated/*.d.ts` against the existing ones.
8. Verify: `pnpm --filter backend build` (compiles TS + admin bundle) and `pnpm --filter backend dev`, confirm the app boots, opens the existing `.tmp/data.db`, and exercise the socket.io flow and a couple of REST endpoints manually (matching this project's existing "verify manually, no automated tests" convention).
9. Re-verify `pnpm --filter frontend build` after the shared-package swap, to close the loop on both apps.

No rollback beyond `git revert` is needed - this is a local/dev-only change with no production deployment step, and the existing `.tmp/data.db`/uploads are untouched by any of the above.

## Open Questions
