## 5. Fix null-safety fallout

- [x] 5.1 Fix the `TS2464` computed-property-key errors in `components/collections-block/filter-block/filter-block.component.tsx`, `components/collections-block/item-image/item-image.component.tsx`, `components/input/input.component.tsx`, and `components/user-list-table/user-list-table.component.tsx` with real narrowing (not `!`) and verify `tsc --noEmit` reports zero `TS2464` errors — root cause: Next's own `*.module.css` typing (`readonly [key: string]: string`) becomes `string | undefined` under `noUncheckedIndexedAccess`. Fixed properly (not a runtime `?? ''` guard on values that always exist) by adding a colocated `*.module.css.d.ts` per affected CSS module declaring its exact class names as plain `string`, which TS picks up automatically over Next's generic wildcard declaration. Also fixed, at the user's direction mid-session: React's `FormEvent`/`FormEventHandler` are marked `@deprecated` in `@types/react@19.2.18` ("doesn't actually exist... use `SubmitEvent`"); replaced with `SubmitEvent<HTMLFormElement>` in all 4 form-submit handlers that used it (`form-login`, `form-register`, both `filter-block` components) — outside the originally-counted 84 errors but a real, verified correctness improvement
- [x] 5.2 Fix the `TS2532` "possibly undefined" errors in `components/collections-block/collection-item/collection-item.component.tsx`, `components/header/donations/donations.component.tsx`, `contexts/collection-context/collection-context.context.tsx`, and `contexts/collection-context/collection-context.utils.ts` by tracing each value back to what the corresponding Strapi API response can actually return, and verify `tsc --noEmit` reports zero `TS2532` errors — traced a genuine runtime bug in `collection-context.context.tsx`'s `handleToggleClick`: after a save round-trip it replaced `userCollections` state with the raw server response instead of re-merging with `defaultUserCollections`, so any collection added to the catalog after a user's last save would be truly `undefined` at runtime (not just a type gap), causing a crash. Fixed by re-merging on every update, matching the initial-mount behavior; added `?.[...]` + sensible defaults (`false`/`{}`/`[]`, matching each field's own established default) at the remaining access sites where the value is genuinely absent-by-design (e.g. a not-yet-toggled item) rather than a bug
- [x] 5.3 Fix the `TS2322`/`TS2769` type-mismatch errors in `contexts/collection-context/collection-context.context.tsx` and `contexts/collection-context/collection-context.utils.ts` (the `Effect`/boolean-map assignment and the `Object.values()` overload mismatch) and verify `tsc --noEmit` reports zero `TS2322`/`TS2769` errors — `TS2769` fixed in `collection-item.component.tsx` with `Object.values(userCollectionsHash[collection.id] ?? {})`; `TS2322` fixed in `collection-context.utils.ts`'s effects-merge reducer by extracting `acc[effect.name]` into a local `existing` variable once, so TS can narrow it inside the ternary instead of re-reading the possibly-undefined indexed access
