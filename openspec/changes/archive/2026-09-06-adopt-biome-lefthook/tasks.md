## 6. Fix real findings

- [x] 6.1 Run `pnpm run check:fix` at the root; review the auto-fixed formatting diff for sanity (no unintended semantic changes - formatting only). Auto-fixed formatting across both apps; also auto-modernized `hasOwn` in `strapi-server.ts` to `Object.hasOwn` (reverted - backend's `lib` didn't include ES2022, see 6.2 - then re-applied once `lib` was bumped).
- [x] 6.2 Run `pnpm run lint`; fix every remaining lint finding by hand (real code changes, not suppressions) in both apps until clean. Real, per-finding scope turned out much larger than design.md's Risk section anticipated: **backend 12 findings, frontend 53 findings** (initial counts were silently truncated by Biome's default diagnostic limit - re-ran with `--max-diagnostics=500` to get the true count). Fixed every one with a real, verified fix - no blanket suppressions. By category:
  - **Backend**: `useNodejsImportProtocol` (`path`→`node:path`); `noUnusedFunctionParameters` (`_reason` prefix); `noConsole` (2x, CLI script's status messages → `console.info`); `noExplicitAny` (2x, `advancedConfigs` cast → a minimal `{ unique_email?: boolean }` type - Strapi's own `CoreStore.get()` returns `Promise<unknown>`, confirmed via its `.d.ts`, so a full interface would overclaim an undocumented shape); `noDoubleEquals` (4x, `!= id`→`!==`) - **caught a real bug in the naive fix**: `update`'s `id` comes from `ctx.params` (a route param, always a string) while `updateMe`'s comes from `ctx.state.user` (a number), both compared against numeric `.id` fields - the existing `!=` relied on type coercion to bridge that; blindly auto-fixing to `!==` would make the `update` handler always reject a user's own unchanged username/email as "taken". Fixed with explicit `Number(...) !== Number(...)` instead. Also bumped `apps/backend/tsconfig.json`'s `lib` to `ES2022` (a strict superset, not touching `target`/`module`) so `Object.hasOwn` - a real Node 20+ feature Biome's `noPrototypeBuiltins` recommends - type-checks; excluded `**/*.example.js` (Strapi's own vendored scaffold templates, one of which already ships `/* eslint-disable no-unused-vars */` from Strapi itself) from Biome's scope entirely rather than edit vendor files.
  - **Frontend, mechanical/low-risk** (~30 findings): `catch (x: any) {}` → optional catch binding (4x, identical empty-catch pattern in `app/**/page.tsx`); `noUselessTernary`; `useLiteralEnumMembers` (`Infinity` → a literal sentinel, since it's not a true enum literal); duplicate CSS property; `noAssignInExpressions` (2x, rewritten as plain `+`/if-else); `noAccumulatingSpread` (3x, O(n²) reduce-with-spread → in-place accumulator mutation, verified behaviorally identical since nothing else references the intermediate accumulator); `noArrayIndexKey` (3x) - one required adding a missing `id: number` field to the `Donation` type (present in the real API response via `flattenApiResponse`, just never declared - every *other* entity type already declares it).
  - **Frontend, `noExplicitAny` batch** (~22 findings across `lib/api/base.ts`, `contexts/auth-context.tsx`, `contexts/boss-context.tsx`, two form components, `lib/get-current-user.ts`, `user-list-table/filter-block`): typed properly against real shapes, not `unknown`-and-done - `flattenApiResponse`/`flattenListApiResponse` rewritten with real type-guard predicates (`isRecord`/`isArray`) instead of `any`; `apiPost` made generic (`<T extends object>`) instead of `Record<string, unknown>` (which rejected named interfaces without index signatures); axios error handling standardized on `axios.isAxiosError<T>()` (fixes a latent bug where `err.response` being `undefined`, e.g. a network error, would have thrown an unrelated `TypeError` instead of the intended error message); **surfaced and fixed two pre-existing latent bugs the `any` typing had been silently masking**: `useState(undefined)` with no type argument (infers as literal `undefined`, not `string | undefined`) in both `form-login`/`form-register` and `user-list-table.component.tsx` - masked before because `any` is assignable to anything.
  - **Frontend, `useExhaustiveDependencies`** (6 findings) - the highest-risk category, each individually verified rather than batch-applied: 5 were genuinely safe excess-dependency removals (`useState` setters and `useRef` ref objects, both guaranteed referentially stable by React - confirmed via each one's own declaration before removing). The 6th (`scrollable.tsx`'s `[recalculateThumbHeight, maxHeight, children]`) was **not** safe - traced the actual CSS (`max-height` on the outer wrapper, not the inner ref'd div) and confirmed a `children`-count change resizes the inner div's `scrollHeight` (overflow content) without changing its own box dimensions, which the component's own `ResizeObserver` effect doesn't detect - removing `children` would make the scrollbar thumb go stale on every list-length change. Left as-is with a documented `biome-ignore`, not "fixed" per Biome's suggestion.
  - **Frontend, accessibility** (`a11y` domain, ~6 findings): two clickable elements converted to real `<button>` (with a matching CSS reset for one, since it inherited default browser button chrome) rather than ARIA-patched `<span>`/`<div>` - Biome's own `useSemanticElements` rule flagged the ARIA-patch as a worse solution than a real button once applied. One (`ItemImage`, conditionally clickable) kept as a `<div>` with `role`/`tabIndex`/`onKeyDown` all conditioned on the same `onClick` truthiness (verified consistent by inspection) with a documented suppression, since Biome's static analysis can't verify cross-prop conditional consistency. The scrollable component's custom scrollbar overlay: discovered the underlying native-scroll div had **no keyboard focus path at all** (neither caller passes `tabIndex`) - a real, pre-existing accessibility gap, not just a lint nit. Fixed by making the real scrollable div focusable (`tabIndex={0}`, the WCAG 2.1.1 "scrollable region focusable" technique - matches axe-core's own rule of the same name) and marking the mouse-only custom scrollbar/thumb overlay `aria-hidden="true"` (redundant with the now-focusable native region, not a workaround). Deleted `public/vercel.svg` (an unused `create-next-app` scaffold leftover, confirmed via full-repo grep, rather than adding decorative alt text nobody would see) instead of "fixing" its missing `<title>`.
  - Discovered mid-fix: `next-env.d.ts` (Next.js's own auto-regenerated file, rewritten by every `next dev`/`next build` with its own double-quote style per `AGENTS.md`) needed the same `.example.js`-style exclusion from Biome's scope - the verification build in task 8.1 regenerated it and reintroduced a "violation" that wasn't there moments before.
