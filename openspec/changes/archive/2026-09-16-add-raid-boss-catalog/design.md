## Context

See `proposal.md` — Why. What follows is only the state that shapes the
approach.

**The source.** `apps/frontend/mocks/raid-bosses/data.ts` was scraped from
giran.info by `mocks/raid-bosses/fetch.js`. Measured, not estimated: 153 bosses,
63 location slugs — 64 locations once the collapse below is undone — 2791 drop
rows, 737 distinct item names, 359 distinct item icons, 96 distinct avatars,
15 dungeon plans, one world map. Images live beside
it under `mocks/raid-bosses/images/` — 5.3 MB of webp, icons 64x64, avatars
256x256 and 64x64, plans ~1600px, the world map 3072x4096.

**Three defects in the source shape the model.**

`itemId` is not an item identity. It is the source's icon field (`drop.i` in
`fetch.js`), and `itemId === basename(icon)` holds for all 2791 rows. 737 item
names map onto 359 icons: `etc_sword_body_i00` is simultaneously Heavy Sword
Edge, Saber Blade, Shilen Knife Edge, Two-Handed Sword Edge and four others.

The `_iNN` suffix is load-bearing, not noise. Stripping it would merge four
groups of genuinely distinct icons — the four enchant-armour scrolls, the four
enchant-weapon scrolls, two buff-slot items, and the Physical and Magical Rings
of Queen Ant. It appears in no item name, no boss name and no boss slug.

Four bosses carry the location slug `x`, under which the scraper collapsed two
distinct Russian-named places.

**Strapi 5.52.3 behaviours verified against the installed packages**, because
each one decides something below:

- A `component` attribute becomes a `relation` at the model level
  (`transform-content-types-to-models.js`), so filtering on component fields
  works through the normal join path.
- `documentId` is generated by `cuid2.createId` as a column default and
  `document_id` is a reserved attribute name — it cannot carry the game's id.
- `uid` fields are auto-generated only by the admin panel: `POST /uid/generate`
  is an admin route. Anything writing through the Content API or the Document
  Service must set the slug itself. `uid` is unique unconditionally
  (`attr.type !== 'uid' && !attr.unique` in the entity validator).
- Media is a morph relation (`files_related_mph`), so one file may be referenced
  by any number of records — one file in this database already sits on 16.
  Strapi does not deduplicate uploads: the same bytes uploaded twice become two
  files.
- `forceMigration` defaults to `true`, so the schema diff drops tables for
  removed content types without being asked.

## Goals / Non-Goals

**Goals:**

- A model that survives the corrections the source needs, rather than one
  transcribed from it.
- A seed that can be run repeatedly against a live database without duplicating
  anything, because it will be run repeatedly while grades are being set by hand.
- Anonymous read access proven end to end by a real request, not by inspecting
  permission settings.

**Non-Goals:**

- Any change to `Boss` or the code that reads and writes it. It stays running
  and is marked deprecated in its description only.
- Deciding whether Carmine's schedule differs by timezone or by a fixed offset.
  The model below expresses either; choosing between them needs `Server`, which
  is a later change.
- Presentation. The list route this change adds is a proof that anonymous
  requests work, not the product's catalogue page.

## Decisions

### A new `RaidBoss` rather than reshaping `Boss`

`Boss` is the live timer, not a catalogue: 34 published rows with Russian names
that only translation relates to the source's 153 English ones, written by
`updateBossTime()` on every kill. Reshaping it in place would break the running
product for the sake of a page that does not exist yet.

*Alternative considered:* one merged type carrying both catalogue and timer
fields. Rejected for now — it forces the boss-to-boss mapping to be done by
hand before anything else can ship, and the mapping is the slow part. The merge
stays possible: it becomes a later change that adds timer fields to `RaidBoss`
and migrates 34 rows.

### Item identity is the name; `itemId` becomes an icon key

Because `itemId` identifies an icon, using it as the item's key would collapse
737 items into 359. Items are keyed by name, which is unique across the source,
and their slug is derived from it — checked, 737 names produce 737 distinct
slugs with no collision, including awkward ones like
`Scroll: Enchant Armor (D-Grade)` → `scroll-enchant-armor-d-grade`.

The source's `itemId` survives as the seed's lookup key for finding the uploaded
icon, and is not stored on the item.

### `BossDrop` as a collection type, not a repeatable component

2791 rows is too many to carry inside the boss record: reading a boss would drag
its whole drop table along, and "which bosses drop this item" would be
unanswerable. As its own type it paginates, filters and reverses.

*Alternative considered:* a repeatable component on `RaidBoss`. Cheaper — no
extra API surface — but it makes the item page impossible, and the item page is
the reason items are a type at all.

### `Grade` as a collection type

Two enumerations, one on `RaidBoss` and one on `Item`, would have to be edited
in two places to add a grade. That is the smaller problem. The larger one is
that Strapi sorts an enumeration as a string, so `sort=grade` returns
`A, B, C, D, NG, S` — the exact reverse of the game's order at the top. A
`Grade` record with an `order` integer makes `sort=grade.order` correct, and
lets a new grade be added from the admin panel without a deployment.

Cost: one populate on every catalogue query, and the seed must create grades
before anything references them.

### Weapon affinities as a lookup type, not components

This started as a repeatable component holding one enumeration, on the grounds
that the vocabulary is six values that will not change and a lookup type would
buy an editable vocabulary nobody asked for. Filtering was the argument that
might have decided it the other way, and it did not — a component is a relation
underneath, so filtering through one works.

Two things changed the answer, neither of them filtering.

The admin panel cannot display a repeatable component usefully. Its accordion
title is `values[mainField]` and only when that is a string; a component's
`mainField` falls back to the parent's `settings.mainField`, which is `name`,
which `weapon-affinity` does not have — so the title resolves to the component's
numeric id and renders empty. Every affinity was a blank collapsed row that had
to be expanded to learn what it said. Declaring the `mainField` does not fix it
either: `syncMetadatas` strips `mainField` from every attribute that is not a
relation, so it would survive one boot.

And a label has to live somewhere. `bow` is a code; "Bow" — or its translation —
is a label, and a label kept beside each usage is the same string stored 120
times, 33 of them for `dagger` alone. Localising that means a copy per boss per
language of a word that needs translating once.

So the six weapon types are records. The boss holds two many-to-many relations
to them, which the panel renders as named chips, and the label is stored and
translated in one place.

The same reasoning would apply to the element and stat modifiers, and is
deliberately not applied: those carry a value of their own (`{element, value}`),
which makes them records rather than vocabulary entries, and no localisation is
wanted yet. Their accordion titles stay blank — 55 and 15 rows, against a fix
that would mean naming their key field `name` purely to satisfy the panel.

### Modifiers as repeatable name-and-value components

The source currently holds only `±1` element modifiers and a single
`pDef: -2` stat modifier, but both vocabularies are expected to grow and the
values to widen. Fixed columns per element and per statistic would need a schema
change for each addition. A repeatable `{ name, value }` component absorbs new
entries without one, and the enumeration of names can be extended in place.

### Respawn in minutes, with a separate weekly schedule

150 bosses have an interval respawn; the source describes it in eight distinct
whole-hour phrasings (base 6, 7, 8, 9, 10, 12 or 14 hours; variance 1 or 2). The
remaining three are epics whose respawn the source records only as the literal
string `Fixed` — no days, no times.

Interval respawns are stored in minutes. Minutes are exact for every value the
source contains and stay exact for sub-hour or multi-day intervals later, and a
timer computes on them directly. The unit shown to a reader is derived by a
formatter; the source's `raw` string is not stored, since it is reproducible.

*Alternative considered:* a `{ value, unit }` pair preserving the authored unit.
Rejected — it makes `1 day` and `24 hours` two different records of the same
fact, and every consumer normalises anyway. If the admin panel showing `360`
instead of `6 hours` becomes a real irritation, a display field can be added
later without touching stored data.

Scheduled respawns are a repeatable `{ weekday, time }` component. Length is
unconstrained, so a boss returning twice a week and one returning five times
need no different treatment, and the three epics are seeded with an empty list
because there is nothing to seed. Per-server variation is added later by giving
that component an optional server relation: entries naming a server override
entries that name none. Nothing stored now has to change for that.

### `Avatar` as its own collection type

96 avatars serve 153 bosses, always as a full-and-miniature pair. Two media
fields on the boss would work — the morph table permits sharing a file — but
nothing would hold the pair together, and an operator replacing one boss's
avatar would silently diverge it from the others that were meant to match. A
type with the pair on it makes the sharing the thing you edit.

### Media Library, with a name-keyed idempotent upload

Assets go through the Media Library because operators must be able to replace
them without a deployment. Since Strapi does not deduplicate, the seed's upload
step looks up an existing file by name first and uploads only what is missing —
otherwise every re-run adds another 566 files.

*Alternative considered:* serving the assets statically from the frontend's
`public/` and storing only a key. Cheaper to seed and identical across
environments, but it puts every image change behind a deployment, which is the
opposite of what was asked for.

### Drop chance is a `float`, not a `decimal`

Strapi's `decimal` maps to `numeric(10,2)` — checked against the created column,
not assumed — so `37.7861` would have been stored as `37.79` and the four
decimal places the spec requires would have been lost on the way in. `float`
maps to `double precision`, which round-trips the value exactly.

The usual objection to binary floats is exact comparison, and it does not apply:
nothing compares a drop chance for equality, it is displayed and sorted.

### `required` on a relation is a form rule, not a guarantee

Both of a drop's relations are marked `required`, which is what the admin form
reads to put an asterisk on them and refuse an empty submit. It stops there:
with both marked required, the Document Service created a drop with no boss, one
with no item, and one with neither. Verified against this schema, not assumed.

So the item — without which a drop means nothing on any path — is checked in the
lifecycle as well. The boss is deliberately not: a drop created from inside a
boss has no boss yet, and refusing it there would break the flow all of this is
meant to smooth. Its net is the raid boss's lifecycle below.

### The boss-and-item pair is enforced from both ends

Attaching a drop to a boss through the boss's relation field is a write to the
*boss*: the drop is created first with no `raidBoss`, and the link lands when the
boss is saved. So `boss-drop`'s own lifecycle never sees the pair on that path.
Measured rather than assumed — a drop made that way ended up with `label = null`
and slipped past the duplicate check entirely.

The boss's lifecycle therefore guards the same constraint from its side, in two
halves either side of the write: the duplicate check refuses before anything is
stored, and the labels are written after, once the links exist. That second half
also keeps a renamed boss's drops in step with it, which nothing did before.

### The boss-and-item pair is enforced by a lifecycle

Strapi has no composite unique constraint, and the pair spans two link tables
(`boss_drops_raid_boss_lnk`, `boss_drops_item_lnk`), so there is no column pair
for the database to constrain either. A `beforeCreate`/`beforeUpdate` lifecycle
on `BossDrop` refuses a second row for a pair that already has one, which covers
the Content Manager, the Content API and the seed alike — and the seed is the
one that matters, since it writes 2791 of these and is expected to be re-run.

### `draftAndPublish` off for the catalogue types

The existing `Boss` carries it, which is why 34 bosses occupy 71 rows. Reference
data has no editorial workflow: a boss is either in the catalogue or not.
Leaving it on would double every table, force the seed to publish each record as
a second step, and make anonymous reads depend on publication state.

### `User.collections` is dropped rather than left dormant

The attribute is a `json` map of which collection items a user had gathered,
non-empty for 63 of 114 accounts. Leaving it would cost nothing mechanically —
it is invisible without the feature — but it would leave the user model carrying
a field nothing writes, nothing reads and nothing explains, and it would keep
`collections` in the self-update allowlist, where every entry is a deliberate
grant of write access to a client. An allowlist entry for an attribute that no
longer exists is the kind of thing that survives for years.

The data does not survive the drop. The backup taken in step 1 of the migration
is the only copy, and this is the reason that step is not optional.

*Alternative considered:* exporting the maps to a file first. Rejected — the
maps key collection and item ids that are themselves being deleted, so the
export would be unreadable the moment it was written.

### Grades are derived, not typed in 890 times

Seeding everything at `NG` and setting it by hand meant 153 bosses and 737 items
of manual work for a value the catalogue mostly implies. So the seed's default
is derived instead of constant.

A boss's grade comes from its level, in bands the operator chose: below 40 `D`,
40-49 `C`, 50-61 `B`, 62 and above `A`. That lands 49/35/25/44. `S` is left
unreachable — the three epics sit at level 72 and take `A` like their
neighbours — and stays in the vocabulary for later.

An item's has two sources, in order of authority. Sixteen items state a grade in
their own name — `Scroll: Enchant Armor (D-Grade)` — and a thing naming its own
grade is evidence about itself, where a drop table is evidence about who carries
it. The rest take the grade of the bosses that drop them, when those agree.

Putting the name first overrules nothing: checked across all sixteen, the two
never disagree, and where the bosses span bands the name picks one of the bands
they span. What it settles is the eight the boss rule could not — the C- and
D-grade scrolls, each dropped across two bands.

That leaves six items neither rule reaches: `Proof of Loyalty`, which falls from
150 bosses across all four bands, two `Ancient Book` and three `Spellbook`. They
keep the default rather than being averaged into a number nobody chose, and the
reader returns their names so the gap is visible instead of implied.

Reviewed afterwards, all six keep `NG` deliberately: quest and skill items, not
equipment, so their grade is absent rather than unknown, and the default happens
to be the right answer. The test names them for that reason — a seventh name
appearing there is a decision to take, not a count to bump.

The hand-set file still wins over both, so this changes the starting point and
not the authority — but it does change what the export should record. Comparing
against `NG` was right only while `NG` was everyone's default and therefore
meant "nobody has set this". With grades derived, nearly every record differs
from `NG`, so that test would have written some 884 entries restating the rules,
and then overridden those rules for every record — changing a band later would
have silently done nothing. The export compares against the derived grade
instead, and writes the disagreements alone.

### Hand-set grades live in their own file, not in `data.ts`

The export has to put the operator's corrections somewhere the next seed reads,
and `data.ts` is not it: its first line says it is generated by
`mocks/raid-bosses/fetch.js` and must not be edited by hand, so anything written
there is lost the next time the source is re-fetched. It also has no grade field
to write into — grade is this catalogue's own idea, absent from the scrape.

So the seed gains a second, hand-owned input:
`apps/backend/src/helpers/catalog-grades.json`, a map of boss slug and item slug
to grade code. Absent or incomplete, everything falls back to `NG`; present, it
wins. The export regenerates it from the database.

Two things this buys beyond correctness. The file is a readable diff, so a
change of grades is reviewable rather than a database-only fact. And the two
inputs stay separated by ownership: the scrape is regenerated by a script and
never hand-edited, the grades are hand-edited and never scraped.

### Display fields are declared in the schemas, not seeded into the store

Strapi decides what to show for a record with
`getDefaultMainField = findFirstStringAttribute(schema) || 'id'`, and
`findFirstStringAttribute` accepts type `string` and nothing else. That leaves
three of the six catalogue types unusable in the admin panel: `Avatar` has only
a `uid` and two media fields, `BossDrop` has only relations and numbers — both
fall back to the cuid — and `RaidBoss` matches `gameId` before `name`, because
`gameId` is declared first.

Two facts decide where the fix goes. `createDefaultMetadata` merges
`schema.config.metadatas.<field>.edit` over what it computed, and
`createDefaultSettings` merges `schema.config.settings`; so both are declarable
in `schema.json`, in git, with no bootstrap machinery. And a relation's label
comes from `getDefaultMainField(targetSchema)` — computed from the target's
*structure*, not read from the target's own `settings.mainField` — so the
display field has to be declared on each relation that points at a type, not
once on the type.

*Alternative considered:* reconciling the configuration from code at boot, the
way `seed-roles-and-permissions.ts` does for permissions. Rejected: that file
makes admin-panel edits stop sticking, which is right for a permission and wrong
for a column layout. An operator rearranging their own view is not a defect.

The catch is that a stored configuration wins over the schema's — `syncMetadatas`
merges the stored values last — so the declarations take effect on a fresh
database and not on one that has already saved a view. Clearing the stored keys
once is a step of this change, not a permanent mechanism.

`BossDrop` cannot be fixed this way at all: every field it has is a number or a
relation, so there is nothing to point at. It gets a `label` string naming the
boss and the item, maintained by the same lifecycle that already guards the
pair. The seed writes it directly — it holds both names already, and 2791 drops
is the wrong place to spend two extra queries each.

### A location carries a `hasDungeon` flag beside its plan

A single component can never show anything in the admin list. `CellContent`
tests `content?.length > 0` whenever the column has no `mainField`, and a
component never gets one — `createDefaultMetadata` assigns `mainField` only
where `isRelation(attribute)`, which is `attribute.type === 'relation'` and so
false for a component. A component instance is an object, `length` is
`undefined`, and the cell renders a dash for every row whether or not there is a
plan behind it.

Declaring the `mainField` does not fix it either: it survives the boot that
creates the configuration and is stripped by the next `syncMetadatas`, which
removes `mainField` from every attribute that is not a relation. One boot of
correctness is worse than none.

So the answer the list needs — does this location have a plan — becomes a
boolean of its own, set by a lifecycle from the presence of the component. It
buys more than a rendered cell: a component is neither sortable nor filterable
in the admin (`searchable: false, sortable: false` in its metadata), and 15
locations out of 64 is exactly the case where narrowing the list matters.

*Alternatives considered:* flattening the plan's five fields onto `Location`,
which would render a thumbnail in the list but dissolve a group of fields that
only mean anything together; and promoting `Dungeon` to a content type, which
renders natively as a relation but adds a type, a migration and seed work for a
record that belongs to exactly one location.

The cost is denormalised state, which is why the flag is written only by the
lifecycle and marked not editable in the panel: a hand-set value that disagrees
with the component would be worse than the dash it replaces.

The list layout is declared alongside it, and drops the `dungeon` column: a new
attribute is not added to a layout that has already been stored, and keeping a
column that can only ever be a dash beside one that answers the same question
would be worse than either alone.

### `race` stays an enumeration

Twelve values, a closed game taxonomy, no ordering wanted, no data to hang off
it. None of the arguments that made `Grade` a type apply.

### Public access

The catalogue types grant `find` and `findOne` to the public role and nothing
else. Writes are refused for every role over the Content API; the admin panel
and the seed are the only ways in. This is the first data in the application
readable without authentication, so the proof is a `curl` with no credentials,
not a screenshot of the permissions screen.

### Drops are fetched per boss, not with the list

The list populates everything a row shows, but not its drops. Measured:
populating drops for all 153 bosses weighs about 450 KB, one boss 3.4 KB — and a
reader opens a handful of rows, not 153. So the tooltip asks for its own boss
when it opens and keeps the answer, which also means a pointer crossing the table
costs nothing (a `mouseEnterDelay` guards the crossing itself).

Two antd details worth recording. A tooltip is capped at 250 px, which wrapped
half the item names onto a third line; the fix is to widen the cap rather than
lift it, since `none` let the box grow to a million pixels. And `placement`
cannot be `right`: a row spans the table, so its right edge is already the
viewport's, and antd shifts the tooltip off-screen rather than flipping it —
the grade and chance columns were what fell outside.

## Risks / Trade-offs

- **Deleting the old content types drops their tables, but not their media.**
  424 `files` rows, 849 files under `public/uploads`, and the
  `files_related_mph` rows that pointed at the removed records all survive the
  schema diff → media cleanup is an explicit step, ordered before the new
  upload so the two sets are never mixed.

- **The seed uploads 566 files.** Slow, and slowest on a first run against an
  empty database → the upload step is separable and idempotent, so an
  interrupted run resumes rather than restarts, and re-running to reload only
  records is cheap.

- **Media is not in version control.** A developer with a fresh database and no
  `public/uploads` gets a catalogue of records pointing at nothing until they
  run the seed → the seed is a single documented command, and the assets it
  reads are in the repository even though the uploads are not.

- **Slugs must be set by the seed.** Auto-generation from `targetField` is an
  admin-panel feature; a record created by the Document Service with no slug
  gets none, and the failure is silent until something tries to address it →
  the seed sets every slug explicitly, and a post-seed check asserts that no
  catalogue record has an empty slug.

- **Grades are seeded at `NG` and set by hand.** Between the first seed and the
  export, the corrected grades exist in exactly one database → the export script
  ships in the same change as the seed, not after it.

- **The two repaired locations are a judgement call.** The source gave Russian
  names and no slug; Eastern Border Outpost and Lachik Habitat are translations
  chosen for this change, not names the source contains → they are named in the
  spec so the choice is visible rather than buried in seed data.

- **`Boss` and `RaidBoss` will coexist and read confusingly.** Two types whose
  names differ by a word, one of which is a timer → `Boss`'s description field
  says so, and the merge is a named later change rather than an open question.

## Migration Plan

Ordered, because several steps are destructive and the order is what keeps them
recoverable.

1. **Back up the database and `public/uploads`.** Everything below is
   irreversible without it.
2. **Frontend first**: remove `components/collections-block/**`,
   `lib/api/collection.ts`, its entries in `lib/api/index.ts`, the collections
   section of `app/profile/[type]`, and the `Collection`/`Effect` types. The
   backend types outlive the frontend that reads them for one step, never the
   other way round.
3. **Purge the old media**: delete the `files` rows and their morph rows for the
   removed collections, then the files on disk. Before the content types go, so
   the relations that identify which media to remove still exist.
4. **Remove `Collection`, `Item` and `Effect`** and the `collection.item`
   component. Their tables drop with them. Drop `User.collections` and its
   allowlist entry in the same step: the attribute and the records it keyed have
   to go together, or the allowlist grants writes to a column that no longer
   exists.
5. **Add the new types and components**, `Grade` first — everything references
   it.
6. **Grant the public role** `find` and `findOne` on the catalogue types.
7. **Seed**: grades, then locations, avatars and items (each with its imagery),
   then bosses, then drops. Assert non-empty slugs and expected record counts.
8. **Add the list route** and verify anonymously with `curl` and in a browser
   with no session.
9. **Set grades by hand, then export** back to the seed source and commit.

**Rollback:** restore the database and `public/uploads` from step 1 and revert
the commit. There is no partial rollback once step 4 has run — the old tables
are gone, and that is why step 1 is not optional.

## Open Questions

Both are deferred deliberately, and neither changes anything this change built.

- **The three epic bosses have no weekly entries.** `Core`, `Orfen` and
  `Queen Ant` are seeded as `scheduled` with an empty `respawnSchedule`, because
  the source records them only as the literal string `Fixed` and names no day or
  time. The shape is in place and the spec permits the empty list; filling it is
  data entry, and the days are not something to invent.
- **Whether Carmine's schedule differs from the European servers by a timezone
  or by a fixed offset.** It decides what a future `Server` record stores, not
  what a `respawnSchedule` entry stores — per-server entries express either
  reading. Worth settling before the timer is built, not before then, and note
  that the two answers disagree for a few weeks a year: Europe/Moscow has not
  observed daylight saving since 2014 while a South American zone does, in the
  opposite half of the year.
