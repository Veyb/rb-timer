## Context

See `proposal.md` for motivation. Facts gathered during exploration, not assumed:

- Route/auth map: `/login`, `/register` are public (per `proxy.ts`'s `PUBLIC_PATHS`); every other route requires a `jwt` cookie. Beyond that, the app has its own 3-tier role gate in `contexts/auth-context.tsx`: `allowed` (viewer/editor/officer) gates `/profile/collections`, `allowedUpdate` (editor/officer) gates editing, `allowedAdminister` (officer only) gates `/users`.
- `backend/.tmp/data.db` is the real dataset migrated from the legacy site: 109 real users (real emails) across roles `Бесправный`(authenticated)/`Анонимный`(public)/`Наблюдатель`(viewer)/`Редактор`(editor)/`Офицер`(officer), and 71 real bosses. No known test credentials exist; passwords are hashed. This is real, sensitive-ish data (real emails) that a test suite must never mutate.
- Schema (confirmed via `sqlite3 .tmp/data.db .schema`): `up_users` (id, username, email, password, ...), `up_roles` (id, name, type — `type` is the stable machine-readable key: `authenticated`/`public`/`viewer`/`editor`/`officer`), `up_users_role_lnk` (id, user_id, role_id — a proper join table with its own `id`, unlike the older join-table shape that caused the Strapi 5 migration's `_lnk` gotcha noted in this project's history; this one is already in the newer shape).
- A fresh self-registration via `/register` lands a user in the `authenticated`/`Бесправный` role (Strapi `users-permissions`' own default) — none of the app's three gates pass for that role.
- `.mcp.json`'s `--cdp-endpoint` browser setup (from the prior `enable-browser-cdp-automation` change) is an interactive, human-in-the-loop tool for AI-agent-driven exploration; it is a different mechanism from Playwright Test's own browser-context lifecycle and is not reused here.
- No `.github/workflows` exists in this repo — there is no CI to wire this into yet.
- Already decided with the user: `webServer` auto-boots both apps with `reuseExistingServer: !process.env.CI` (Playwright's own documented pattern — locally, an already-responding `localhost:3000`/`:1337` from the developer's own `pnpm dev` terminals is detected and left completely alone, both on start and on teardown; only a server Playwright itself launched gets torn down). Auth setup goes through the real login/register forms in the browser, not a direct API shortcut, so a broken form is itself something the suite would catch.

## Goals / Non-Goals

**Goals:**
- Detect "the app doesn't start" or "a core screen crashes" regressions during upcoming large refactors, with minimal maintenance burden.
- Never mutate or put at risk the 109 real migrated user accounts.
- Be runnable from a clean checkout with zero manual setup (no human has to create a test account by hand first).

**Non-Goals:**
- Deep feature/edge-case coverage, or testing the specific bugs already fixed elsewhere.
- Any assertion that mutates real data through UI actions (toggling a collection item, editing a real user, killing a boss).
- Wiring a CI workflow — this change only makes `pnpm test:e2e` work locally; running it automatically on push is a separate, later decision once the repo has CI at all.
- Replacing or redefining the existing `pnpm test` (`eslint .`) script.

## Decisions

**Run against the real `backend/.tmp/data.db`, not an isolated test database.**
Setting up a second Strapi instance pointed at a separate SQLite file (a cleaner "textbook" E2E setup) would need its own `DATABASE_FILENAME` override, its own seed script for bosses/collections/effects, and a reset step between runs — real infrastructure work disproportionate to "just tell me it starts and doesn't crash." Running against the existing dev database, restricted to read-only assertions plus one dedicated fixture account, gets the safety property that matters (never touching the 109 real users) without that infrastructure cost. Revisit this decision if the suite ever needs to grow into mutation-testing territory.

**One idempotent fixture user, login-first.**
The setup project always tries the real login form first with fixed fixture credentials (a synthetic address, e.g. `e2e-fixture@rb-timer.local` — not resembling any of the 109 real emails). Only on a login failure does it fall through to the real registration form, then logs in. This means: first run on any given `data.db` creates the fixture user once; every subsequent run (including every future `pnpm test:e2e` invocation on the same machine) just logs in — no accumulation of throwaway accounts. If `data.db` is ever regenerated (as already happened once during the Strapi 4→5 migration), the fixture self-heals on the next run.

**Role upgrade via direct SQLite write against `up_users_role_lnk`/`up_roles`, scoped strictly to the fixture email — implemented as a `backend/scripts/` script, not frontend code.**
A freshly-registered user cannot reach `/profile/collections`, `/profile/management`, or `/users` at all (all three require `viewer`/`editor`/`officer`). Since Strapi's `users-permissions` plugin has no public self-service "change my role" action, and creating a Strapi admin-API token just for this one-time setup step is heavier than the alternative, `backend/scripts/e2e-fixture-role.js` (run via `pnpm run e2e:fixture-role <email>`, using `better-sqlite3`, already a `backend` dependency) does: look up the fixture user's `id` in `up_users` by email, look up the `officer`-typed role's `id` in `up_roles` (never hardcode the numeric id — types are stable, numeric ids are not guaranteed across environments), delete any existing `up_users_role_lnk` row for that `user_id`, insert a new one linking to the officer role. Idempotent: skip entirely if the fixture user is already linked to the officer role. This mirrors this project's own established pattern for exactly this kind of fix (the `boss.world` NULL fix and the `_lnk` table `id` fix during the Strapi 5 migration both went through direct SQLite writes, not backend code changes).

The script deliberately lives in `backend/`, not `frontend/e2e/`, even though it's only ever invoked from the Playwright setup step: `better-sqlite3` is a native module already compiled and installed for `backend`, and this repo's README explicitly calls out that `backend`/`frontend` are kept independent (separate `node_modules`, no shared code) specifically to avoid one app's dependencies leaking into the other's. The Playwright setup spec invokes it as a plain subprocess (`node scripts/e2e-fixture-role.js <email>` with `cwd` set to `backend/`), which is a loose, dependency-free boundary — no cross-package `require`, no duplicated native module install.

**storageState via a Playwright "setup project," not a fixture per test file.**
Standard Playwright Test pattern: a dedicated `setup` project runs once before all other projects, performs the login-or-register-then-role-upgrade flow through the real browser, and saves `page.context().storageState()` to a git-ignored file. Every other test project depends on `setup` and loads that file via `use: { storageState: ... }`, so authentication happens exactly once per full test run, not once per spec file.

**Smoke assertions only: page reaches ready state, one key element visible, zero uncaught console errors — no deep interaction.**
Matches the stated non-goal of strict coverage. A `page.on('console', ...)`/`page.on('pageerror', ...)` listener asserting no errors were logged, plus one `expect(page.getByRole(...)).toBeVisible()` per screen, is enough to catch "this screen now throws" without asserting anything about the screen's exact contents (which would break on every unrelated refactor — exactly the fragility the user wants to avoid given the app "will undergo large-scale changes").

**`channel: 'chrome'` instead of Playwright's bundled Chromium.**
The machine already has a real Google Chrome install (confirmed present, and already relied on by the `enable-browser-cdp-automation` change). `channel: 'chrome'` makes Playwright Test launch that already-installed system Chrome directly, which — per Playwright's own docs — skips the `playwright install` download step entirely (that step is only needed for the default bundled Chromium/Firefox/WebKit). Avoids an unnecessary ~300MB duplicate browser download for no real benefit here; the tradeoff (bundled Chromium tracks upcoming Chrome changes early, which matters more for sites shipping to production browsers at scale) doesn't apply to this project's "does it start" smoke-test goal.

**Centralized `data-testid` registry over `getByLabel`/`getByText` locators — a mid-implementation revision.**
The initial implementation used Playwright's own generally-recommended locator order (role/text/label). The user pushed back with a fair concern: labels are visible copy, and this app is explicitly expected to churn — a wording/i18n change unrelated to functionality would break a label-based locator. Checked Playwright's own docs to settle it rather than going on instinct: "Testing by test ids is the most resilient way of testing as even if your text or role of the attribute changes, the test will still pass," with the explicit trade-off noted immediately after — "testing by test ids is not user facing." For a typical project, that trade-off favors role/label locators (they double-check real user/accessibility behavior). For this suite specifically — pure smoke-testing, explicitly not meant to assert on content, on a codebase expected to undergo large-scale changes — the resilience test ids provide matters more than the accessibility cross-check. Landed on: `frontend/constants/test-ids.ts` as the single source of truth (one flat, nested-by-screen object, e.g. `TEST_IDS.loginForm.identifier`), imported by both the application components (which set `data-testid={...}`) and the e2e suite (which locates via `getByTestId(...)`) — the same "one shared source, both sides import it" shape already used for e.g. `constants/screen-breakpoints.ts`. A `MayHaveTestId` shared prop type (`frontend/types/test-id.types.ts`) documents the `'data-testid'?: string` contract on any custom component that needs to accept and forward one. Only `components/input/input.component.tsx` needed an actual code change to thread the prop through to its underlying `<input>` (it explicitly destructures a fixed prop list rather than spreading `...rest`); `Button` needed nothing, since `styled-components`'s `styled(AntButton)` and antd's own `Button` both already forward arbitrary `data-*` attributes. Kept exactly one `getByLabel` assertion in the setup flow as a lightweight supplementary accessibility sanity check, rather than dropping label-awareness entirely.

## Risks / Trade-offs

- [Risk] The role-upgrade script and the running `backend` (started by `webServer`) both open `backend/.tmp/data.db` concurrently — a raw `better-sqlite3` write from a second process while Strapi's own connection is live could hit a transient "database is locked" error, unlike the project's prior SQLite fixes which were applied with the backend stopped. → **Mitigation**: run the role-upgrade write in WAL-friendly mode with a short retry-with-backoff (a handful of attempts, ~50-100ms apart) around the single `INSERT`/`DELETE`; it's one tiny write, so even a naive retry loop is more than sufficient — no need for a bigger connection-pooling story.
- [Risk] "Read-only smoke assertions only" is a convention enforced by code review, not by any technical guard — a future test file could still add a mutating action against the real dataset without anything stopping it. → **Mitigation**: a short comment at the top of the e2e test directory stating the constraint explicitly, so it's visible to whoever adds the next test.
- [Risk] The fixture's `storageState` file contains a real (if low-stakes) session cookie. → **Mitigation**: already covered — `backend/.tmp` is gitignored for the DB; the `storageState` output path must be placed under a path also covered by `.gitignore` (e.g. `frontend/playwright/.auth/`, add if not already ignored).
- [Risk] Running e2e tests against a developer's own already-running dev server (`reuseExistingServer: true` locally) means test runs are not perfectly reproducible/isolated from whatever manual state that developer's session is in (e.g. mid-edit, HMR not yet settled). → **Mitigation**: acceptable for this suite's stated purpose (fast local smoke-check, not a hermetic CI gate); CI (when it exists) gets `reuseExistingServer: false` and therefore a clean boot every time.

## Migration Plan

1. Add `@playwright/test` to `frontend/package.json` devDependencies; add `frontend/playwright.config.ts` with the `webServer` array (backend + frontend, `reuseExistingServer: !process.env.CI`).
2. Add the fixture role-upgrade helper script (`better-sqlite3` against `backend/.tmp/data.db`, scoped to the fixture email, idempotent, with retry-on-lock).
3. Add the Playwright `setup` project: login-first-then-register via the real browser forms, call the role-upgrade helper, save `storageState`.
4. Add smoke-test spec files for `/`, `/profile/collections`, `/profile/management`, `/users`, each depending on the `setup` project's `storageState`.
5. Add `frontend/package.json`'s `test:e2e` script; gitignore the `storageState` output path.
6. Rollback: delete the new files and the `test:e2e` script/devDependency; the one extra `up_users`/`up_users_role_lnk` row for the fixture account can be left in place harmlessly or deleted manually — no other system state is affected.
